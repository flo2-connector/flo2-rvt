# flo2-rvt

flo2-rvt lets an agent working through [flo2.io](https://flo2.io) have real Revit, in Autodesk's cloud, read a person's Revit model (`.rvt`) and change it through a fixed vocabulary of changes. It is an MCP server written in TypeScript that drives Autodesk Platform Services' **Automation API** (Design Automation v3) on the person's **own** Autodesk app, with a short-lived token flo2.io hands it for each job.

It runs three jobs, each paid by processing time on the person's app, each confirmed by the person on flo2.io first:

- **The probe** (v0) reads the model and changes nothing. Since add-in 0.12.0 it can also save families the person names out of the model as family files (`.rfa`), which an edit can then load into any model.
- **The edit** (v1) applies a change list to the model and saves the result as a **new** `.rvt`. The person's model is never changed. The edit's output `.rvt` can be the next edit's input, so changes stack.
- **The new model** (v6, add-in 0.13.0) makes a model the design does not have yet, from Revit's own project with no template or from a template file (`.rte`) the design keeps, fills it with its first change list in the same job, and saves it as a new `.rvt` ([below](#a-new-model-add-in-0130)). Its result is the next edit's input, as an edit's is.

**The probe.** Real Revit 2024 opens the model and changes nothing. It returns three files, which flo2.io saves into the person's design as new files:

| File | What it holds |
| --- | --- |
| `report.json` | The levels with their elevations in feet and millimetres, the sheets by number and name, the linked files (Revit links and CAD links or imports), element counts by category, the Revit release the file was saved in and the engine's version and build, and the warnings stored in the model. Since add-in 0.10.0, what an edit places new content by: every wall, floor and door type the model holds (`types`, by family and name, with a wall's thickness, a floor's and a door's sizes), its placed rooms (`rooms`: number, name, level, area, point and boundary, in shared and internal coordinates; Revit's IFC export holds no rooms), and how its shared coordinates sit on its internal ones (`coordinates`). Since add-in 0.11.0, every foundation type too (`types.foundations`: each Structural Foundations family type and wall foundation type, with its length parameters, type or instance, their values, and whether Revit holds them read-only or by a formula), which an edit's foundation sizes name. |
| `sheets.pdf` | Every printable sheet, in sheet-number order, in one PDF. Absent when the model has none. |
| `model.ifc` | Revit's own IFC export: IFC4 Design Transfer View, with base quantities. |
| `family1.rfa` … `family8.rfa` | Since add-in 0.12.0, each family the probe was asked to save (`save_families`) that the model holds as a loadable family, as a family file in Revit 2024's format; the n-th name asked goes back as `family<n>.rfa`, and the gateway keeps it as `<family>.rfa`, the name an edit loads it under ([below](#saving-families-out-of-the-model-add-in-0120)). Absent for a name not saved. |

**The edit.** Real Revit 2024 opens the model, applies the change list in order, and returns up to four files, which flo2.io saves as new files beside the model:

| File | What it holds |
| --- | --- |
| `report.json` | Per change: what it named and matched, what it deleted, what Revit deleted with a host, changed or added on its own, the messages Revit raised, what is still in the model (what Revit would not delete, and what is still tied to an emptied level, each with why), and whether it was applied, applied in part, rolled back or not applied, judged from what is really left. Since add-in 0.10.0, what each change added (`added`: the element's id, GlobalId, family, type and level, a wall's ends, length and height, a floor's area beside its outline's, a room's number, name and area, a door's host wall and where it stands; since add-in 0.11.0 a footing's or pile's point, top and bottom, rotation and every length parameter as Revit holds it, a wall footing's host wall, width, thickness and length; since add-in 0.13.1 what a footing or pile was placed by, the correction applied for its top, and the IFC class the add-in set; since add-in 0.14.0 a door's width and height as its placed type holds them, the type it was copied from, its family file and every length parameter of it and its type beside each size asked), and what came of each family file the list named (`families`, since add-in 0.14.0 with the category each needed). Each element is named by its element id, IFC GlobalId, category and Revit class, and model elements are counted apart from Revit's internal ones. Then the levels after the edit, how the model was saved, and the model's stored warnings. Always written. |
| `model.rvt` | The edited model, a **new** file: a new central model, with its worksets, when the input is workshared. Absent when no change was kept. |
| `sheets.pdf` | The edited model's printable sheets in one PDF, in sheet-number order: since add-in 0.15.0 the sheets of a drawing set the list made (`add_drawing_set`, [below](#a-drawing-set-change-list-version-7-add-in-0150)) among them. Absent when it has none, or no change was kept. |
| `model.ifc` | Revit's own IFC export of the edited model, with the probe's options. Absent when no change was kept. |

flo2-rvt's design lives in reflow2, design `6ab9996ca4bdbc45` (reached through the hub); the settled choices behind it are in flo2's design.

## How a job travels

```
agent ──tools/call──▶ flo2.io gateway ──127.0.0.1:8740, bearer──▶ flo2-rvt ──person's APS app, job token──▶ Autodesk
                          │  holds the person's APS secret             │  holds no secret, keeps no token
                          │  mints a short-lived token per job         │  never opens the .rvt itself
                          ◀──── signed URLs of the outputs ────────────┘
```

0. Before the person is asked to approve a job, flo2.io's gateway calls `rvt_setup_check`: flo2-rvt reads, by GETs alone, whether the person's app holds the AppBundle and the job's Activity at `prod`, at this flo2-rvt's add-in version. If not, the person is told so in plain words and offered the one-time setup (`rvt_setup_run`, [below](#setting-up-a-persons-autodesk-app)); no job is made and nothing is uploaded.
1. `rvt_probe_start` or `rvt_edit_start`: flo2-rvt reads the job's Activity on the person's app first (an app that does not hold it is refused in plain words, before any bucket or upload), then makes (or finds) the person's transient bucket, streams the `.rvt` from flo2.io's short-lived download link into it through signed S3 upload URLs, checks the bytes against the size and SHA-256 flo2.io stated (no match, no job), uploads an edit's change list beside it, and submits a WorkItem with `limitProcessingTimeSec`. Autodesk's Revit reads the inputs and writes the outputs into the same bucket with the same token.
2. `rvt_job_status`, polled: Design Automation's own state, passed through. On success, the status result carries signed download URLs of the outputs for the gateway, which downloads them, saves them add-only, and strips them before the agent sees the result.
3. Autodesk deletes everything in a transient bucket after 24 hours.

## The contract with flo2.io's gateway (v8)

v1 is v0 with the edit job added: one more tool, `rvt_edit_start`, its outputs, and an edit's report summary on `rvt_job_status`. Nothing in v0 changed, so a v0 gateway still works for the probe. v2 (0.3.0) adds three counts to an edit's report summary and counts only model elements in its `elements_deleted`; nothing else changed, and a v1 gateway, which passes the summary through, still works. 0.4.0 keeps v2: the summary is unchanged, and its `left_on_level` now leaves out parts of kept elements, which were never left.

v3 (0.5.0) adds the setup of a person's own Autodesk app from flo2.io: two tools the gateway calls itself and never offers an agent (`rvt_setup_check`, `rvt_setup_run`), the hidden context's `setup` (what the person approved), `_meta["flo2.io/error"]` on a refused start, and a start that reads its Activity before it uploads anything. Nothing of v2 changed: a v2 gateway still works, and on an app flo2-rvt was never set up on its start is refused before any upload, in plain words.

v4 (0.12.0) adds the family files a version 4 change list names (`family_file`, [below](#foundations-change-list-version-4-add-in-0110)): the hidden context's `families` on `rvt_edit_start`, which the gateway fills from the design as it fills `input`, and the start result's `family_files`, what flo2-rvt uploaded. Nothing of v3 changed: a v3 gateway still works for every list that names no family file, and one that does is refused by name before anything is uploaded.

v6 (0.14.0) adds a new model made and filled in one job ([below](#a-new-model-add-in-0130)): one tool, `rvt_new_model_start`, its own Activity (`Flo2RvtNew`, which a setup registers beside the other two and `rvt_setup_check`'s `job` may name, `new`), the hidden context's `template`, the start result's `new_model`, and a new model's `report_summary` (an edit's, with `new_model` and `types_held`). Change-list version 5 (`add_level`) is read by every job that takes a list. Nothing of v5 changed: a v5 gateway offers no new-model job, and its edits run as before.

v7 (0.15.0) reads change-list version 6 ([below](#doors-from-a-family-file-change-list-version-6-add-in-0140)): `add_door`, as `add_footing` and `add_pile`, may name a door family file the design keeps (`family_file`) and size a new type copied from the named one (`sizes`, `new_type`). The hidden context's `families` and the start result's `family_files` carry a door's family file as they carry a foundation's, on `rvt_edit_start` and `rvt_new_model_start` alike; its family must be in the Doors category, and a list that names one file for a door and for a foundation is refused before anyone is asked. An edit's report names, per door, the type it was copied from, its family file and every size it holds beside each asked (what flo2's check measures; a door's sizes need no calc record), and per family file the category it needed. Nothing of v6 changed: a v6 gateway, whose copy of the schema reads versions 0 to 5, refuses a version 6 list before the person is asked, and every list it hands over runs as before.

v8 (0.16.0) reads change-list version 7 ([below](#a-drawing-set-change-list-version-7-add-in-0150)): `add_drawing_set`, a conceptual drawing set of the model as the list leaves it, each view on a numbered sheet, which the job's `sheets.pdf` prints. It names no file, so the hidden context and the start results are v7's. An edit's `report_summary` adds `sheets_added`, and its report a change's `drawing_set` and `totals.views_added` and `totals.sheets_added`. Nothing of v7 changed: a v7 gateway, whose copy of the schema reads versions 0 to 6, refuses a version 7 list before the person is asked, and every list it hands over runs as before.

v5 (0.13.0) adds the families a probe saves out of the model ([below](#saving-families-out-of-the-model-add-in-0120)): `rvt_probe_start`'s `save_families`, said back in its result; each family saved, an output `family<n>.rfa` whose `_meta["flo2.io/outputs"]` entry carries its `family`, the `file` it loads under and its `sha256`; and the probe's `report_summary`'s `families_saved` and `families_not_saved`. Nothing of v4 changed: a v4 gateway sends no `save_families`, and a probe without them saves nothing.

### Transport

- **Streamable HTTP** on `127.0.0.1`, path `/mcp`, port `FLO2_RVT_PORT` (default `8740`). Loopback only; a foreign `Host` or `Origin` is refused (403).
- Every request carries `Authorization: Bearer <FLO2_RVT_LOCAL_TOKEN>` (32+ characters, from the environment). Anything else is 401.
- Built on the MCP TypeScript SDK **v2.4.0** (`@modelcontextprotocol/server` 2.4.0 with `@modelcontextprotocol/node` 2.1.2), through its `createMcpHandler`: a fresh server per request, no session. It serves the 2025 protocol revisions (an `initialize` with `2025-06-18`, or a `tools/call` on its own) and the 2026-07-28 revision.
- A client sends `Accept: application/json, text/event-stream`. Answers to 2025-revision requests come as a short SSE stream (`event: message`, one `data:` line holding the JSON-RPC response), as Streamable HTTP allows.

### Tools for the gateway (v3)

flo2.io's gateway calls these itself; its door never offers them to an agent.

| Tool | Arguments | Result (`structuredContent`, also as JSON text) |
| --- | --- | --- |
| `rvt_setup_check` | `job`?: `probe`, `edit`, `new` (v6) or `all` (default, every one); `plan`?: boolean | `{ ready, state, why?, owner, nickname_set, expected: { addin_version, appbundle, activities }, found: [{ kind, id, state, addin_version?, version?, why? }], setup: { available, why?, addin_version, bundle_sha256?, bundle_bytes?, nickname?: { now, will_set, keeps_client_id }, deletes_nothing: true } }`. `state` is `ready`, `not_set_up` (something the job needs is missing) or `outdated` (there, but registered by another flo2-rvt). By GETs alone: `forgeapps/me`, the AppBundle `<owner>.Flo2RvtProbe+prod` and each Activity the job needs, each by its qualified id. With `plan`, `setup.nickname` says what the setup's nickname step does: `now` is the nickname the app has, which it keeps; a setup never sets one (since 0.5.1), so `will_set` is always `null`, and `keeps_client_id` is `true` whenever the app has no nickname. Annotated `readOnlyHint: true`. |
| `rvt_setup_run` | none | `{ state: "set_up", owner, owner_how, owner_note?, addin_version, bundle_sha256, bundle_bytes, appbundle: { id, version, created, alias }, activities: [{ id, version, created, alias }], monthly_hours: { requested, reported }, check }`, where `check` is `rvt_setup_check`'s result read back after the setup. Refused, and Autodesk never asked, without the hidden context's `setup`, when this server holds no AppBundle or one whose bytes are not its sha256, or when `setup.bundle_sha256` is not this server's AppBundle. A step Autodesk refuses stops it with a refusal that names the step in plain words and by its call, gives Autodesk's status and words beside them, and says nothing was deleted and the setup can run again; the server logs it as `setup_failed` (`operation`, `status`, `autodesk_said`). In both, the client id is written `…` and its last four characters. Annotated `readOnlyHint: false`, `destructiveHint: true` (it moves aliases and sets the cap). |

An Activity is `ready` when its body is the one this flo2-rvt registers (engine, the AppBundle it names, its command line, each parameter's verb and local name, no other required parameter) and its description names this add-in version: every AppBundle and Activity description ends with `(flo2-rvt add-in <version>)`, the add-in's own `<Version>` (`addin/Flo2RvtProbe.csproj`, held equal to `ADDIN_VERSION` in `server/src/names.ts` by a test). A description that names another version, or none (an app registered by flo2-rvt 0.4.0 or earlier), is `outdated`, and a setup brings it up to date. The version is the add-in's, not the bundle's sha256, so a new flo2-rvt whose add-in has not changed needs no new setup. *Assumed until the first live setup*: that Autodesk returns an Activity's description as it was given, as the reference's example shows; an answer with no description at all is judged by its body alone, so a setup is never asked for again and again.

`state` is Design Automation's own status, passed through: `pending`, `inprogress`, `success`, `cancelled`, `failedLimitDataSize`, `failedLimitProcessingTime`, `failedDownload`, `failedInstructions`, `failedUpload`, `failedUploadOptional`, and any it adds. `processing_seconds` runs from the start of the input download to the end of the output upload, as Autodesk counts its limit, rounded up. Every tool carries annotations: a `title`, `readOnlyHint: false`, `openWorldHint: true` (and `destructiveHint: false`, since no job changes the person's file; `idempotentHint` false for the starts, true for status).

`change_list_sha256` is the SHA-256 of the change list in its canonical form (every object's keys sorted, no whitespace): the exact bytes flo2-rvt uploads as `changes.json`, which the add-in reads and names again in `report.json`. flo2.io computes the same form, so it can check that what runs is what the person approved.

### Hidden context

The gateway sets `params._meta["flo2.io/job"]` on every `tools/call`:

```json
{
  "person_id": "opaque",
  "design_id": "…",
  "aps": { "access_token": "…", "expires_at": "2026-10-31T12:59:59Z", "client_id": "…" },
  "input": { "download_url": "https://…", "file_name": "….rvt", "size": 123, "sha256": "…" },
  "families": [{ "family_file": "Footing-Rectangular.rfa", "download_url": "https://…", "size": 393216, "sha256": "…" }],
  "limits": { "max_processing_sec": 1800 },
  "setup": { "monthly_hours": 2, "bundle_sha256": "…" }
}
```

- A call without it, or with it malformed, is refused (a tool error the agent reads). The agent's arguments are untrusted and bounded; everything that decides what happens at Autodesk comes from this context.
- `input` is required on `rvt_probe_start` and `rvt_edit_start`. The file must be a `.rvt`. `rvt_new_model_start` takes none, and refuses one handed over: it makes the model.
- `template` (v6) is read on `rvt_new_model_start` alone, `{ template_file, download_url, size, sha256 }`, there exactly when the start names a `template_file`, and that file (case counts): the `.rte` the design keeps, handed over as a family file is, at most 128 MiB (134,217,728 bytes). A start with `units` that carries one, or any other job that does, is refused. It is fetched into the transient bucket as `template.rte` and refused with no job unless it is `size` bytes long with that `sha256`, then handed to the new-model Activity's optional input `template`.
- `families` (v4) is read on `rvt_edit_start` (and since v6 `rvt_new_model_start`, the same way) alone: one entry for each family file the change list names (`family_file`: a footing's or pile's, and since v7 a door's), handed over as the model is. `family_file` is exactly the list's (case counts): the name of the `.rfa` the design keeps, which the gateway resolves in the design as it resolves `file`; `download_url` a short-lived link to its bytes; `size` its bytes; `sha256` of its bytes, read when the person was asked. Before anything is asked of Autodesk, flo2-rvt refuses the edit, naming the file, unless `families` holds every family file the list names exactly once and nothing else, each at most 32 MiB (33,554,432 bytes) and all at most 64 MiB (67,108,864 bytes); a list names at most 8. A probe that carries any is refused. Each is fetched from its link into the transient bucket like the model, and refused with no job unless it is `size` bytes long with that `sha256`; the WorkItem hands the n-th the list names (in the order it first names them) to the edit Activity's optional input `family<n>`, which the add-in reads as `family<n>.rfa`. The start result's `family_files` names each as uploaded, for the gateway to hold to what the person was shown, and the add-in's report gives each file's bytes and sha256 again, as it read them (`families`).
- `expires_at` may be an ISO-8601 time, or seconds (or milliseconds) since the epoch.
- **The token must outlive the job.** Autodesk's Revit stores the outputs with the same token when the job ends, so `rvt_probe_start` refuses a token valid for less than the job's time limit plus 600 s. A freshly minted two-legged token (3,599 s) covers the longest job (1,800 s).
- The time limit is the lower of `max_minutes × 60` and `limits.max_processing_sec`.
- flo2-rvt uses only this token, keeps it for no longer than the call (the WorkItem carries it to Autodesk), and never logs it.
- `setup` (v3) is required on `rvt_setup_run` and read nowhere else: what the person approved on flo2.io. `monthly_hours` (1 to 744) is the cap the setup sets on their app (Autodesk's `limitMonthlyProcessingTimeInHours`); `bundle_sha256` is the sha256 of the AppBundle they were shown, which must be the one this server holds.

### Results for the gateway

When a job reaches `success`, the status result carries:

- `_meta["flo2.io/outputs"] = [{ name, signed_url, expires_at, size, content_type }]`, one per output that exists (`report.json` `application/json`, `sheets.pdf` `application/pdf`, `model.ifc` `application/x-step`, and an edit's `model.rvt` `application/octet-stream`). An optional output the job did not write is left off the list. The URLs stay usable for 15 minutes.
- Since v5, a family a probe saved is an entry `{ name: "family<n>.rfa", signed_url, expires_at, size, content_type: "application/octet-stream", family, file, sha256 }`: `family` exactly as the model holds it, `file` the name it loads under in an edit (`<family>.rfa`, since Revit names a family it loads by its file), which is the name the gateway keeps it by, and `sha256` of its bytes as the add-in saved them, which the gateway holds what it downloads to. flo2-rvt asks Autodesk for a family output only once the probe's report names it saved, in the report's own shape (its `file` the family's name and `.rfa`, its output one of the names asked); one whose bytes in the bucket are not the size the report gives is withheld and logged (`family_output_withheld`), never served under a family it may not hold.
- `_meta["flo2.io/usage"] = { processing_seconds, workitem_id }`.

`failedUploadOptional` (an optional output could not be stored) carries the same two keys for the outputs that were stored.

A refused call (v3) may carry `_meta["flo2.io/error"] = { code, billed, autodesk_said? }`, so the gateway acts on the case rather than on the words. Its one code, `not_set_up`, means the person's app does not hold what the job needs: a start found no Activity before it uploaded anything (`billed: false`, nothing uploaded), or Autodesk refused the WorkItem with a 400 or 404 naming a missing Activity or AppBundle (`billed: false`, `autodesk_said` its words; the model went only to the transient bucket). The text says so in plain words, says nothing was billed, and says to ask flo2.io for the one-time setup and start the job again, with Autodesk's own words quoted after.

### Names

- `job_id`: a v4 uuid flo2-rvt mints before the upload.
- Bucket key: `flo2rvt-` + the lowercased client id, reduced to OSS's `[-_.a-z0-9]` and cut to fit 128 characters, + `-t`. Transient (24 h).
- Objects: `<job_id>/input.rvt`, an edit's `<job_id>/changes.json` and family files (`<job_id>/family1.rfa` ...), a new model's `<job_id>/new-model.json` and `<job_id>/template.rte`, `<job_id>/report.json`, `<job_id>/sheets.pdf`, `<job_id>/model.ifc`, an edit's `<job_id>/model.rvt`, and **`<job_id>/workitem.json`**, a small job record (the WorkItem id, the activity, the job, an edit's `change_list_sha256` and its family files' inputs, sizes and sha256s, the time limit, when it was submitted). The WorkItem id only exists after the inputs and outputs are named, so it cannot be encoded in the `job_id`; the record is how a status call after a restart, with the `job_id` and a fresh token alone, finds the WorkItem and knows which job's outputs to list (a record without `job` is a probe's). An in-memory cache saves the read while the process lives.
- Activities: `<nickname>.Flo2RvtProbe+prod`, `<nickname>.Flo2RvtEdit+prod` and, since add-in 0.13.0, `<nickname>.Flo2RvtNew+prod`, where the nickname is what `GET /forgeapps/me` answers: the app's nickname, or its client id when it has none. All run the one AppBundle, `<nickname>.Flo2RvtProbe+prod`. Each description ends with `(flo2-rvt add-in <version>)`.

### Token scopes the gateway requests

```
bucket:create bucket:read data:create data:write data:read code:all
```

| Scope | For |
| --- | --- |
| `bucket:create` | `POST /oss/v2/buckets` (the transient bucket) |
| `bucket:read` | `GET /oss/v2/buckets/{key}/details` (a 409 on create is checked to be this app's bucket) |

## The change list

`schema/change-list.schema.json` is the one JSON Schema of the change list an agent hands the edit job and the new-model job: version 7, the element reference (an IFC GlobalId, or a level by name or by its storey's GlobalId), and thirteen change kinds: `delete_elements_on_level`, `delete_elements_by_global_id`, `set_level_elevation` and `move_levels_together`; adding new content, `add_wall`, `add_floor`, `add_room` and `add_door`; adding foundations, `add_footing`, `add_wall_footing` and `add_pile`; adding levels, `add_level`; and drawing the model, `add_drawing_set`. Version 1 (flo2-rvt 0.6.0, add-in 0.5.0) added `move_levels_together` and a level move's `groups_in_the_way`, and a list that uses either says `"version": 1`; a list of version 0's vocabulary reads as it always did, as version 0 or 1. Version 2 (flo2-rvt 0.7.0, add-in 0.6.0) adds a level move's `constraints_in_the_way`, and a list that uses it says `"version": 2`; a list of version 1 reads as it did. Version 3 (flo2-rvt 0.11.0, add-in 0.10.0) adds `add_wall`, `add_floor`, `add_room` and `add_door`, and a list that uses any of them says `"version": 3`; a list of version 2 reads as it did. Version 4 (flo2-rvt 0.12.0, add-in 0.11.0) adds `add_footing`, `add_wall_footing` and `add_pile`, and a list that uses any of them says `"version": 4`; a list of version 3 reads as it did. Version 5 (flo2-rvt 0.14.0, add-in 0.13.0) adds `add_level`, and a list that uses it says `"version": 5`; a list of version 4 reads as it did. Version 6 (flo2-rvt 0.15.0, add-in 0.14.0) adds `add_door`'s `family_file`, `sizes` and `new_type`, and a list that uses any of them says `"version": 6`; a list of version 5 reads as it did. It is checked three times before Revit acts on it, each time against the same rules: by flo2.io's gateway (before the person is asked), by the server (`server/src/change-list.ts`, which reads the schema file itself through zod's `fromJSONSchema`), and by the add-in (`addin/src/Edit/Logic/ChangeListCheck.cs`, which walks the JSON with closed key sets, so a key the add-in would not read is refused rather than skipped). On top of the schema all three hold the same limits: at most 512 KiB in canonical form, at most 20,000 GlobalIds in all, no elevation, move or point beyond Revit's model extent (20 miles from the internal origin), no move by zero, what version 1 added only in a version 1 list (2 and 3 the same), a wall's ends two points and its height more than nothing to a level other than its own, a floor's outline each corner once, not crossing itself and with an area, and a door's `wall_change` exactly one `add_wall` change before it; and, since version 4, a footing's or pile's point, `top_offset` and every size within the model extent, `new_type` only beside `sizes`, a wall footing's `wall_change` exactly one `add_wall` change before it, and at most 8 family files in one list; and, since version 5, a new level's elevation within the model extent and no two `add_level` changes naming one new level; and, since version 6, a door's `family_file`, `sizes` and `new_type` only in a version 6 list, its sizes and `new_type` held as a foundation's, and no family file named by a door and by a footing or pile (its family cannot be in both categories); and, since version 7, `add_drawing_set` only in a version 7 list, its `levels` and `empty_levels` only beside plans, and one drawing set in a list. `schema/test/change-lists.json` holds the cases and the verdicts every side must reach; the server's and the add-in's tests both read it.

### What each change kind does

Changes run in order, **each in its own Revit transaction**. Lengths are converted to Revit's foot exactly (1 ft = 304.8 mm).

**A level** is named by `level_name`, matched exactly (case and spaces count), or by `global_id`, the GlobalId of the `IfcBuildingStorey` Revit's exporter writes for it (see below). A level that is not found makes the change `not_applied`, and the report lists the model's levels.

**`delete_elements_on_level`** deletes every **model element on the level**, keeps the level, and lists what is still tied to it afterwards. An element is on level L when it is a model element and either its Revit level is L (`Element.LevelId`) or one of its base or reference level parameters is L: a wall's base constraint, a column's base level, a level-based family's level, a beam's or brace's reference level, a floor's level, a footprint roof's base level, a stair's or railing's base level, a duct's or pipe's reference level, a room's level, a group's level, a part's base level, or a family instance's **Schedule Level** (`INSTANCE_SCHEDULE_ONLY_LEVEL_PARAM`, a beam's or a face-hosted family's "Schedule Level": what Revit schedules on L, and what its IFC exporter files under L's storey) (`addin/src/Edit/LevelRules.cs`).
- *A model element*: not a type, not drawn in one view only (annotation, detail items), in a category of Revit's Model kind, and not a level, grid, reference plane, base point, Revit link or CAD import, view, or part of a sketch.
- *Hosted elements go with their host*: a door or window in a deleted wall is deleted by Revit with it (Revit's `Document.Delete` deletes "any elements that are totally dependent upon" the ones named, and pinned elements "with no warnings"). The report lists them under `deleted_by_revit`.
- *A member of a group* is never deleted alone: it goes with its group, which is on L by the same rule.
- *Elements that only reach the level from below are kept*: a wall whose top constraint is L, a column whose top level is L, a stair whose top level is L. So are views, sheets, schedules and tags of elements that are kept, and the level itself.
- *Elements Revit will not delete alone* (`DocumentValidation.CanDeleteElement`: a curtain wall's mullions and panels, a door in a curtain wall, a wall's foundation) are not asked for; Revit deletes them with their host. After the transaction each is judged against what Revit deleted (`addin/src/Edit/Logic/Reconcile.cs`): deleted with its host, it is listed under `deleted_with_host` (done); still in the model, under `could_not`.
- *What is left is listed, never deleted by a guess.* After the transaction the add-in reads the model again and lists under `left_on_level` every element still tied to L, each with what ties it (`tied_by`) and why it was not taken (`reason`, `why`; `addin/src/Edit/Leftovers.cs`, `addin/src/Edit/Logic/LeftOnLevelRules.cs`): tied by its Revit settings (its level, a level parameter, a family hosted on the level itself) but not a model element, a member of a group on another level, or tied only by a setting the rule does not read; or filed by Revit's own IFC exporter under L's storey: an element with **no Revit level** (by its height, below), or one on a level that is not a building storey. An element with no level is listed, never deleted.
- *A part goes with its owner* (since 0.4.0). The IFC storey ties an element (`tied_by: ifc_storey`) only when the exporter exports it as a product of its own (below). One it exports only with another element is that element's part: a sketch's curves (a stair's sketch boundary, a rail's path extension lines) go to the sketch's owner, a top rail, handrail or a handrail's support to its railing, a curtain grid line, mullion or panel to its curtain wall, roof or system, an opening to what it cuts. When its owner is still in the model, the part is listed under it in `left_on_level.parts_of_kept_elements` (each owner by element id, GlobalId, category and Revit class, with `exists` and how Revit named it, `found_by`), and is not left. When its owner is gone, it is an orphan, left behind: listed in `elements` with `reason: orphaned_part` and the gone `owner`, and counted. One the exporter does not export on its own that names no owner, or that the exporter skips for another reason (its Export to IFC is No, a secondary design option, a demolished phase), and that no Revit setting ties to L, is listed in `left_on_level.not_exported` with the exporter's reason, and not counted. 0.3.0's re-run of the first live edit counted 14 parts of kept elements (four stair sketch lines, seven rail path extension lines, a top rail, two curtain grid lines) as left on the emptied level beside its 2 real leftovers, the wardrobes; the job's own IFC filed none of the 14 there.
- The change is `applied` when nothing it took is still in the model and no model element is left on the level; otherwise `applied_in_part`, and `why` says what is left. Views of the level, its sketch planes and other elements that are not model elements are listed in `left_on_level` and counted apart; they never make a change `applied_in_part`, and neither do parts of kept elements or what the exporter does not export.

**Which elements Revit's IFC exporter exports as products of their own**, from the same source and commit (`addin/src/Edit/Logic/ExportFilter.cs`, read in Revit by `ExportReader` in `addin/src/Edit/Leftovers.cs`), in the order the exporter applies it:
- *Its collector* (`Utility/ElementFilteringUtil.cs`, `GetExportFilter` and `GetClassFilter`): never a curtain grid line, an opening, a split face or a sketch; curves only when the export writes annotations (on for the IFC4 Design Transfer View the add-in exports; `Utility/ExportOptionsCache.cs`, `ExportAnnotations`); not centre lines, decals, property lines or topography contours; only elements in no design option or a primary one (`GetDesignOptionFilter`), and only new, existing or phaseless ones in the model's last phase (`GetPhaseStatusFilter`; `ExportOptionsCache.UpdateForDocument`).
- *Its Export to IFC setting* (`ShouldElementBeExported`, `GetExportElementState`): No on the element, or on its type when the element leaves it By Type, exports nothing.
- *Its class's exporter* (`Exporter/Exporter.cs`, `ExportElementImpl`): a curve only when it is a model curve or a curve by points, not a curve of another element's sketch (`ExporterIFCUtils.IsCurveFromOtherElementSketch`), of some length, with a sketch plane (`Exporter/CurveElementExporter.cs`, `ShouldCurveElementBeExported`, `ExportCurveElement`); a family instance unless it is invisible or hosted by a curtain wall, roof or system, which exports it (`Exporter/FamilyInstanceExporter.cs`, `ExportFamilyInstanceElement`; `Exporter/CurtainSystemExporter.cs`, `IsCurtainSystem`, `IsLegacyCurtainElement`); a railing's top rail, handrails and their supports only inside the railing's `IfcRailing` (`Exporter/RailingExporter.cs`, `CollectSubElements`, `ExportRailing`).
- Anything else is taken as exported on its own: where the rule cannot tell, the element is listed as left, never hidden. The rule is restated in this project's own terms; no code is copied (`THIRD_PARTY_NOTICES.md`).

**The storey Revit's IFC exporter files an element under**, as Autodesk's open-source exporter does it (github.com/Autodesk/revit-ifc, branch `Release_24.x.x`, commit `887c3d3e`, `Source/Revit.IFC.Export`; `addin/src/Edit/Logic/Storeys.cs` and `addin/src/Edit/Leftovers.cs`):
- *The storeys* (`Exporter/Exporter.cs`, `BeginDocumentExportCommon`): the levels sorted by `ProjectElevation`, then by id (`Utility/LevelUtil.cs`, `FindAllLevels`). A level with its "Building Story" setting on (`LEVEL_IS_BUILDING_STORY`; on when absent, `IsBuildingStory`) is an `IfcBuildingStorey`, as high as the distance to the next building storey at another elevation (0, open above, for the highest). A level that is not a building storey shares the storey of the building storey before it.
- *An element with a level*: its `IfcSpatialContainer` (or `OverrideElementContainer`) parameter first, when it names a level (`Utility/ParameterUtil.cs`, `OverrideContainmentParameter`); else its base level (`LevelUtil.GetBaseLevelIdForElement`: a wall's base constraint; a family instance's, or its top-level instance's, base level, then **Schedule Level**, then reference level; a truss's or an extrusion roof's reference level; a stair's base level; a duct's or pipe's reference level; a slab edge's floor's level; else `Element.LevelId`; a railing with none, its host's), and that level's storey.
- *An element with no level* (`Toolkit/PlacementSetter.cs`, `commonInit`): by the height of its bounding box's lowest point (a sketch-based line: its sketch plane's origin): the storey whose span holds it, a span running from 10 cm below the storey's elevation (`LevelUtil.LevelExtension`) to 10 cm below the next one's. Below every span, or with no bounding box, the lowest storey.

**`delete_elements_by_global_id`** deletes the elements its GlobalIds name. A GlobalId that names no element is listed under `not_found`; one whose element an earlier change already deleted, under `already_gone` (done, not missing); one that names a level, a type, a view, a link, a group member or anything else that is not a model element, or that two elements carry, under `could_not` with the reason. What is hosted in a deleted element goes with it, as above; an element it names that Revit will not delete alone, and deletes with another it names, is listed under `deleted_with_host`, as above.

**`set_level_elevation`** sets the level's elevation, `relative_to` either `project_origin` (Revit's `Level.ProjectElevation`) or `elevation_base` (Revit's `Level.Elevation`, measured from the level type's Elevation Base: the project base point or the survey point). Revit can set only `Elevation`; a target from the project origin moves it by the same amount, since the two differ by a fixed offset. **What is attached to the level moves with it, by Revit's own regeneration**: elements whose base or reference level it is keep their offset from it (the report counts them as `attached`), elements whose top is constrained to it change height (`top_constrained`), and hosted elements follow their hosts. The report gives the level's elevation before and after, both ways, in feet and millimetres, and every element Revit modified. A level already at that elevation is `not_applied`. Each `set_level_elevation` runs alone: while one level has moved and the next has not, what spans the two is stretched or compressed, and Revit judges that model. To shift several levels by one amount, use `move_levels_together`.

**`move_levels_together`** (version 1) moves every level it names by one offset, `by` (up when positive), **in ONE transaction**: the add-in sets each level's `Elevation` and commits once, and Revit regenerates the model at the commit (Revit 2024's API reference for [`Document.Regenerate`](https://www.revitapidocs.com/2024/22468e2c-9772-8478-0816-c9759aa43428.htm): "when a transaction is committed there is an automatic call to regenerate the document"; its developer's guide, [Handling Failures](https://help.autodesk.com/cloudhelp/2014/ENU/Revit/files/GUID-52A45CC1-3BB4-48B4-BFC7-F6F8666C2AA4.htm): posted failures are processed "at the end of a transaction"). So Revit judges only the model with every level moved, in which what lies between two moved levels is meant to keep its shape and move whole: a wall from one to the other keeps its height, a model group spanning them its definition. Revit can still reshape an element on its own while it regenerates: on Autodesk's sample house (2026-11-03) a precast stair that already broke its own 181 mm riser rule went from 3 to 4 desired risers, kept its 3 drawn ones, and stopped 137.5 mm short of its top. So since add-in 0.7.0 a level move measures every model element before it (its bounding box, and a stair's desired and actual risers and riser height) and every element Revit touched after it, and the report's `reshaped_by_revit` lists each one whose shape changed, with `totals.elements_reshaped_unexpected` (`addin/src/Edit/Logic/Reshapes.cs`, measured by `addin/src/Edit/Shapes.cs`). An element is `expected` only when the move makes it change, and says why (`expected_as`, `why_expected`): `top_constrained`, or, since add-in 0.8.0, `building_pad_surface`, the ground surface a building pad on a moved level cuts (Revit's `BuildingPad.AssociatedTopographySurfaceId`), which goes deeper or shallower with its pad into ground that stays (`because_of_element_id` names the pad). The proof of add-in 0.7.0 in real Revit flagged both of the sample house's pad surfaces, each 238.125 mm taller, as unexpected. Since add-in 0.8.0 each element also gives its size change on every axis (`size_change_mm`: a room-separation line 36 mm longer reads 0, 36, 0, where its height shows nothing), a stair its climb (`stair.climb_before_mm`, `climb_after_mm`: actual risers times riser height; Revit's box of that precast stair is one riser taller than its climb, so the box fell 172.2 mm where the climb fell 129.2; since add-in 0.9.0 a stair run its climb too, `run`: its actual risers and `StairsRun.Height`, "the elevation span between run's base elevation and top elevation", since 0.8.0 named that stair's run by its box alone, and a run or a landing the stair it belongs to, `part_of_element_id`, from `GetStairs()`), and a room its number, name, level and area (`room`: room 201 Entry Hall grew from 30 to 31 m2, which its box does not say); a room whose area changed is reshaped even when its box did not. Every warning stored in the model also names the elements it flags (`warnings[].elements`), and since add-in 0.8.0 a kept level move lists the warnings standing after it that did not before (`warnings_added`, empty when none; `addin/src/Edit/Logic/WarningsAdded.cs`): the sample house's lowering added "A wall and a room separation line overlap", naming the wall and the line beside that room. That Revit never judges the intermediate states is inferred from those two documented facts; a real job proves it. Only what ties a moved level to one that is not moved changes height (a wall from an unmoved basement up to a moved first floor), and the report lists it as `top_constrained`; what sits on a moved level is `attached`. Each level is named once (the same level by name and by its storey's GlobalId is refused, `not_applied`), and a move by zero is refused. The report's `move` gives the offset and each level's elevation before, asked for, and after (`addin/src/Edit/Logic/LevelMoves.cs`); the change is `applied` when every level is where it was asked to be, and `applied_in_part`, naming each that is not, otherwise.

**A model group in the way of a level move** (`set_level_elevation` or `move_levels_together`; `addin/src/Edit/Logic/GroupsInTheWay.cs`, read in Revit by `addin/src/Edit/Groups.cs`). Revit moves a group with its levels when the move does not change it. When it would change a group whose type has one instance, Revit allows it with a warning ([`AtomViolationWhenOnePlaceInstance`](https://www.revitapidocs.com/2024/8c04e8dd-57da-0e4a-981c-907d48a2e79f.htm)), which the add-in dismisses. When it would change a group whose type is placed more than once, Revit raises an error ([`AtomViolationWhenMultiPlacedInstances`](https://www.revitapidocs.com/2024/d7ddc84c-5270-2672-4e81-02e83f2b3546.htm): "Changes to groups are allowed only in group edit mode ... You may use the "Ungroup" option to proceed with this change by ungrouping the changed group instances"); the API has no group edit mode. A group is kept, then, only by not changing it: by moving every level it is tied to by one amount, together. What happens otherwise is the change's `groups_in_the_way`:
- *`refuse`*, what a change that says nothing does: the move is rolled back, nothing is ungrouped, and the report's `groups.in_the_way` names each group Revit named (instance id, GlobalId, name, type and its id, copies of the type, reference level, members), with `why` saying how a person can let it through.
- *`ungroup`*, only once the person agreed: the move is tried first with every group kept. If Revit rolls it back for groups in the way and for nothing else, it is tried again in a new transaction that first ungroups ONLY the group instances Revit named (the outermost group holding each element it named), with [`Group.UngroupMembers`](https://www.revitapidocs.com/2024/086b03c7-6a46-a825-1cae-9739a7819d4f.htm) ("removes all the members from the group and deletes the group"; the members stay where they are), then moves the levels; a nested group Revit names next is added, at most three tries in all. Revit's own "Ungroup" resolution is not taken inside failure processing: the API reference does not document which resolution type it is, while `UngroupMembers` is documented. The report's `groups.ungrouped` names every group instance ungrouped, with `linked: false`, and `groups.note` says in plain words that those copies are no longer linked to their type or its other copies (editing one later does not update the others), and that the original model is untouched. `attempts` lists every try with every message Revit raised in it. A try that hits another error too (such as a sketch that no longer fits its face) is not retried: ungrouping would not clear it, and nothing is ungrouped.
- For a kept move, `groups.moved_with_levels` lists every group tied to a moved level that is still a group in the model after it, each with what the move was expected to do to it (`moves_with_its_levels`, `reshaped_one_instance`); `totals.groups_ungrouped` counts the instances ungrouped.

**A constraint in the way of a level move** (since flo2-rvt 0.7.0, add-in 0.6.0; `addin/src/Edit/Logic/ConstraintsInTheWay.cs`, read in Revit by `addin/src/Edit/Constraints.cs`). A locked dimension or alignment (a padlock in Revit) is an element of its own, in Revit's Constraints category, that holds elements to each other: a pile cap locked to the Foundation level and to a floor. When a move would pull them apart, Revit raises an error, `DimensionFailures.RegenConstraintUnsatisfied` ("Constraints are not satisfied"), naming the elements and the constraint, and its dialog offers "Remove Constraints". Measured on Autodesk's sample house: lowering all six levels together by 9 3/8 in was refused for two pile caps. What happens is the change's `constraints_in_the_way` (change-list version 2):
- *`refuse`*, what a change that says nothing does: the move is rolled back, nothing is removed, and the report's `constraints.in_the_way` names each constraint Revit named (element id, category, `dimension` and whether it is locked) and the elements it ties (`ties`: id, GlobalId, name, category), with `why` saying how a person can let it through (the architect releases them in Revit, or the list says `remove`).
- *`remove`*, only once the person agreed: the move is tried first with every constraint kept. If Revit rolls it back for constraints in the way, and for model groups only when the change also says `groups_in_the_way: "ungroup"`, and for nothing else, it is tried again in a new transaction that first removes ONLY the constraint elements Revit named that are in the Constraints category (`Document.Delete`, in the Revit API reference), then moves the levels; at most four tries in all. Revit's own resolution is not taken inside failure processing, as for groups. The report's `constraints.removed` names every constraint removed with what it tied, and `constraints.note` says in plain words that those elements are no longer held to each other (the architect may want to lock them again) and that the original model is untouched. `attempts` lists every try, with `removed_first`.
- Since add-in 0.6.0 every message in `revit_messages` also says what each element it names is (`element_categories`), Revit's id for the kind of failure (`definition`), and the resolution Revit offers for it (`revit_offers`), which the add-in reports and never takes.

### New content (change-list version 3, add-in 0.10.0)

Four change kinds add elements, each in its own transaction like every change, each **from a type the model already holds**: nothing is loaded or made. A type is named by its family and its own name, exactly (`"wall_type": { "family": "Basic Wall", "type": "Interior - Partition" }`): Revit's IFC export names each element `<family>:<type>:<element id>`, and the probe's report lists every wall, floor and door type the model holds (`types`). `family` may be left out when no two families hold a type of that name. A type the model does not hold makes the change `not_applied`, and `why` lists the types it does hold (`addin/src/Edit/Logic/Placement.cs`, `TypeMatch`).

**Where a point is.** Every point is a plan point, `{ "x", "y", "unit" }`, in the change's `coordinates`, which a change must say:
- `shared`: Revit's shared coordinates. This is the frame Revit's own IFC export of the model is written in with the exporter's default coordinate base, which flo2-rvt's probe and edit both use, so **x and y read from the model's IFC** (the probe's `model.ifc`, or the last edit's), in that file's length unit, go straight in. The probe's report gives each placed room's point and boundary in it too (`rooms[].location_shared_ft`, `rooms[].boundary_shared_ft`, in feet).
- `internal`: Revit's internal coordinates, from the model's internal origin, as the Revit API takes points (the probe's `rooms[].location_internal_ft`).

The two are one rotation and one offset apart, read from the project base point as Autodesk's open-source IFC exporter places its site for the shared coordinate base (github.com/Autodesk/revit-ifc, branch `Release_24.x.x`, commit `887c3d3e`: `Utility/ExportOptionsCache.cs` makes `SiteTransformBasis.Shared` the default, and `Utility/GeometryUtil.cs` `GetSiteLocalPlacement` places the IfcSite, the root of every element's placement, by a rotation of the project base point's angle to true north, `ActiveProjectLocation.GetProjectPosition(...).Angle`, and an offset of `BasePoint.SharedPosition` less the rotated `BasePoint.Position`). So shared = R(angle)·internal + offset; the report gives both (`coordinates`: `angle_deg`, `offset_x_ft`, `offset_y_ft`), and every point it names in both frames. A point's height is never a coordinate: a new element stands on its level. *Assumed until the first live run*: that an element placed at shared x, y lands at x, y in the edited model's own IFC.

**`add_wall`** places a straight wall on `level`, along the line from `start` to `end` (its location line), of `wall_type`, with `Wall.Create`. `top` is `{ "height": <length> }` (Revit's Unconnected Height) or `{ "top_level": <level> }` (Revit's Top Constraint: the wall rises to that level, and follows it when it moves); a top level not above the wall's own is not applied. `joins`, `join` unless said, lets Revit join its ends to the walls they meet, as drawing a wall does; `do_not_join` disallows both (`WallUtils.DisallowWallJoinAtEnd`). The report gives the wall's ends as Revit holds them, its length, height, thickness, location line and joins.

**`add_floor`** places a floor on `level` over `outline` (3 to 500 corners, in order, the last joined back to the first; its top at the level) of `floor_type`, with `Floor.Create`, after Revit's own `BoundaryValidation.IsValidHorizontalBoundary`. An outline naming a corner twice, crossing itself or with no area is refused before Revit is asked. The report gives Revit's area (`HOST_AREA_COMPUTED`) beside the outline's own, its thickness and its corners.

**`add_room`** places a room with `name` and `number` on `level` at `point`, as placing a room in Revit does (`NewRoom`): it fills the region the walls or room separation lines around the point enclose, including walls an earlier change of the list added. Revit makes a room at any point, an unbounded one where nothing encloses it, so the change reads the room's area inside its transaction and rolls itself back when there is none, saying so; it is never left as an unbounded room. The report gives its number, name, level, area, perimeter, point and phase.

**`add_door`** places a door of `door_type` into a straight wall: `host` is `{ "global_id": ... }` for a wall the model has, or `{ "wall_change": "w1" }` for one an earlier `add_wall` of the list added (a wall change that was not kept makes the door `not_applied`). `point` is taken to the nearest point of the wall's location line, and must lie between its ends and within the wall's thickness of the line. The door stands on the wall's level (`NewFamilyInstance` with the wall as host). The report gives its host wall (element id, GlobalId, the change that made it), where it stands (in both frames, and how far along the wall), how far the point named was off the line, and its type's width and height. Since change-list version 6 a door may also come from a door family file and be sized as a new type, as a footing may ([below](#doors-from-a-family-file-change-list-version-6-add-in-0140)).

### Foundations (change-list version 4, add-in 0.11.0)

Three change kinds add a foundation, each in its own transaction like every change. `add_footing` and `add_pile` place a **Structural Foundations family instance** (`NewFamilyInstance(point, symbol, level, StructuralType.Footing)`); `add_wall_footing` places a **wall foundation** under a wall (`WallFoundation.Create`). Revit's category does not tell a pile from a footing, so the change kind does.

**Where its type comes from.** A footing's or pile's type (`footing_type`, `pile_type`) is named by family and type as a wall's is, and is one the model holds, or one of the family a **family file** the design keeps brings (`family_file`: a `.rfa`, saved by Revit 2024 or older, by its file name in the design). flo2.io hands the file over with the job ([the hidden context's `families`](#hidden-context)), and the add-in loads each family file the list names before any change runs, each in a transaction of its own (`Document.LoadFamily`), from a copy under its own name, since Revit names a family it loads from a file by the file's name without `.rfa`. A family the model already holds under that name is used as it is, **never reloaded or overwritten**. A file Revit 2024 cannot load, or whose family is not a Structural Foundations family, is rolled back, and every change naming it is `not_applied` with why. With `family_file` the type is looked up in that family alone, and a `family` named beside it must be that family's. The report's `families` say what came of each file: `loaded`, `held` or `not_loaded`, with its bytes and sha256 as the add-in read them and the family's types. A wall foundation type is a Revit system family, so `add_wall_footing` takes no family file: it places a wall foundation type the model holds.

**Sizes.** `sizes` names up to 16 length parameters, by their names as the probe lists them for the type (`types.foundations[].sizes`), each a length: `{ "Width": { "value": 1.5, "unit": "m" } }`. A parameter of the type is set only on a **copy of the type** made under `new_type` (`ElementType.Duplicate`), never on the type the model holds, since that would resize every element of it already in the model; a size that is a type parameter without `new_type` is `not_applied`. A type the family already holds under `new_type` (one an earlier change made) is placed again only when its sizes are those asked; otherwise the change is `not_applied`. A parameter of the element is set on the new element. A name that is neither, one Revit holds read-only or by a formula, or one Revit places the element by (its offset from its level, which `top_offset` sets) is `not_applied`, naming the length parameters the type and the element have (`addin/src/Edit/Logic/Foundations.cs`, `FoundationSizes`). flo2.io requires every size and every non-zero `top_offset` to be a result of the calc record the edit names (`numbers_from`).

**`add_footing` and `add_pile`** stand at `point` (in `coordinates`, as every point does) on `level`, **their top at the level's elevation plus `top_offset`** (0 when left out; negative is below), whatever their family's insertion point (since add-in 0.13.1). A family puts its insertion point where its author chose: Autodesk's `M_Pile Cap-600 Pile` has it at its top, `M_Pile-Steel Pipe` at its embedment line, its type's *Minimum Embedment* below its top, which the first live edit measured (2026-11-06: the pile's top stood 152 mm higher than asked). So the add-in places the element with its insertion point there (moved there should Revit set it elsewhere), then, in the same transaction, reads its top as Revit holds it, its read-only *Elevation at Top* (`BuiltInParameter.STRUCTURAL_ELEVATION_AT_TOP`), measured from the project base point and taken to internal feet by the base point's own height (`BasePoint.Position.Z`), and applies the difference: on the element's offset from its level (the one parameter Revit places it by that a change may set and that holds where its insertion point stands from its level: *Height Offset From Level* on Revit's own foundation families), so it keeps its level and the offset reads in Revit as what it is; with none, or two that could be, by `ElementTransformUtils.MoveElement`. A family whose insertion point is its top needs nothing. One Revit holds no *Elevation at Top* for stands by its insertion point there, as before 0.13.1, and its change's `why` says so. A footing is turned by `rotation_deg` in plan, counterclockwise in the change's coordinates (in shared coordinates, the frame's angle is taken off for Revit's internal turn); a pile hangs plumb from its top and takes no turn. The report gives where its insertion point, its top and its bottom stand (internal feet), what it was placed by (`placed_by`: `elevation_at_top` or `insertion_point`), Revit's *Elevation at Top* and the project base point's height beside it, its bounding box's top, the correction applied and how (`top_correction_ft`, `top_corrected_by`: `offset_from_level`, naming the parameter, or `move`), its top above its level beside `top_offset`, its rotation both ways, and every length parameter of it and its type as Revit holds them, each size asked beside it; a footing or pile whose top is still not where `top_offset` put it, or whose size is not as asked, reads `applied_in_part`.

**IFC.** Revit's IFC exporter (revit-ifc, branch `Release_24.x.x`, commit `887c3d3e`, `Utility/ExporterUtil.cs` `GetExportType`, lines 1965-2052) takes an element's IFC class first from its own *Export to IFC As* (`IFC_EXPORT_ELEMENT_AS`), else its type's *Export Type to IFC As*; with neither, from the export table Revit holds for its category (Revit's own code, `ExporterIFCUtils.GetIFCClassName`, which revit-ifc's source does not hold), then revit-ifc's own category map (no entry for Structural Foundations), and only when all of those leave it unknown or a proxy does it make a Structural Foundations instance placed as a footing an `IfcFooting`. The first live edit (2026-11-06) wrote a pile cap with nothing set as an `IfcSlab` (`BASESLAB`), which only that table can have given. So since add-in 0.13.1 **the add-in sets the class of every footing and pile it places**: the new element's own `IFC_EXPORT_ELEMENT_AS` to `IfcFooting` on every `add_footing` and `IfcPile` on every `add_pile` (the live edit's pile, set so, came out an `IfcPile`); its type, and every other element, is left as it is, and one Revit holds no settable *Export to IFC As* on is rolled back. The report gives both values, the class set (`ifc_entity`) and `ifc_entity_basis: "set_by_addin"`; a footing or pile that reads `applied` had its class set and read back. A wall footing has nothing set: revit-ifc writes every wall foundation an `IfcFooting` (`Exporter/FootingExporter.cs`), so its `ifc_entity` is `IfcFooting` with `ifc_entity_basis: "predicted"`. Neither is read from the IFC: the job's own `model.ifc` is the measurement.

**`add_wall_footing`** goes under `wall`, one the model has (`{ "global_id": ... }`) or one an earlier `add_wall` of the list added (`{ "wall_change": "w1" }`), of `wall_footing_type`, sized by `sizes` on a copy of the type. Revit hangs it along the wall's base. The report gives its host wall (element id, GlobalId, the change that made it), its width, thickness and length as Revit holds them, its top and bottom, and every length parameter beside each size asked.

### Doors from a family file (change-list version 6, add-in 0.14.0)

Revit's own project with no template holds no door family (measured 2026-11-06, in flo2-rvt's design: `fact:revits-no-template-project-in-design-automation-holds-one-level-and-generic-wall-and-floor-types-2026-11-06`), so a new model's doors need a family from the design. As the owner settled it (`dec:a-door-type-is-held-or-loaded-from-an-rfa-the-design-keeps-and-sized-as-a-new-type`), `add_door` goes the foundation path above, step for step (`addin/src/Jobs/EditJob.Additions.cs`), and nothing of its own:

- **`family_file`**: a door family file (`.rfa`, Revit 2024 or older) the design keeps, by its file name, handed over and loaded before the list's changes run exactly as a footing's is: a family the model already holds under that name is used as it is, never reloaded or overwritten. Its family must be in the **Doors** category: one in another (a footing family named for a door) is rolled back, or, held, not used, and the doors naming it are `not_applied` with why. Each family file a list names is held to the category its changes need (`addin/src/Edit/Logic/Foundations.cs`, `FamilyFiles.CategoryFor`: Doors for a door's, Structural Foundations for a footing's or pile's), so one file serves doors or foundations: a list that names one from a door and from a footing or pile is refused by all three checks. With `family_file` the door's type is looked up in that family alone, and a `family` named in `door_type` must be its.
- **`sizes` and `new_type`**, as a foundation's. A door's sizes are named as its family names its length parameters (Autodesk's `Single-Flush` holds `Width` and `Height` as type parameters). A type parameter is set only on a copy of `door_type` made under `new_type` (`ElementType.Duplicate`), never on a type the model holds; a `new_type` the family already holds is placed again only when its sizes are those asked, so a list placing many doors of two sizes copies two types and places each again by its name; a parameter of the door is set on the new door; and its *Sill Height* or *Head Height*, where Revit places it in its wall, is no size. flo2.io requires no calc record for a door's sizes, unlike a foundation's: a door's size is read from the source model (an IFC door's `OverallWidth` and `OverallHeight`), as a wall's height is.
- **The report**, per door (`added[].door`, fields added): its width and height as its placed type holds them (the copy's, when it was sized), `copied_from`, `new_type`, `new_type_was` (`copied` or `held`), `family_file`, `family_was`, and `sizes`: every length parameter of its type and itself as Revit holds them, each size asked beside it. A door whose size is not as asked reads `applied_in_part`, and the report check holds a door read `applied` to every size asked (`ReportCheck`, `DoorCheck`). Each family file in `families` gives the category it needed (`category_needed`).
- **The probe** lists a door type's width and height (`types.doors`), not its length parameters by name, and a family file it has not seen it lists not at all: a size the door's type does not hold is `not_applied`, naming the length parameters the type and the door do hold.

### A drawing set (change-list version 7, add-in 0.15.0)

Step 5 of flo2-rvt's plan (`cap:cloud-revit-makes-plan-views-and-sheets-of-added-content`), which the owner brought before step 4's roofs and stairs (`dec:idea-a-conceptual-drawing-set-comes-before-roofs-and-stairs`, settled 2026-11-09): **`add_drawing_set`** makes a conceptual drawing set of the model as the list's earlier changes leave it, each view on a numbered sheet of its own, which the job's existing PDF export prints with the model's other printable sheets into `sheets.pdf`, in sheet-number order. Which views a set holds is the owner's still to settle (`dec:idea-a-conceptual-set-holds-elevations-sections-3d-and-a-room-schedule`); it is built to the set he was told it would hold until he does, and a room schedule is later. Put it last, after what it draws. It runs in one transaction, as every change does, and each view and each sheet in a sub-transaction of it (`ChangeRunner.Part`), so a view Revit will not make is reported with Revit's words and the others go on; a set none of whose views could be made is rolled back. What the set holds and how each piece is decided is `addin/src/Edit/Logic/DrawingSets.cs`; what Revit is asked, `addin/src/Jobs/EditJob.DrawingSet.cs`.

| Kind (`views`) | What is made | Sheets |
| --- | --- | --- |
| `plans` | A floor plan of every level (`ViewPlan.Create`, the first Floor Plan view type by name), or of the levels `levels` names, by name or storey GlobalId. A level nothing stands on (no model element on it by its Revit settings, as `delete_elements_on_level` reads it) gets its plan unless `empty_levels` says `leave_out`; a level the model does not hold is reported as not made. | `A-101`, `A-102` ... from the lowest level up, whatever order `levels` names them in |
| `elevations` | The building's four elevations, each named by the face it shows and looking at it from outside: an `ElevationMarker` beyond that side, at its middle, past the plans' crop, and the one of its slots whose view looks at the face (`CreateElevation`; the API reference does not say which slot looks which way, so each is tried and the others deleted). | `A-201` north, `A-202` east, `A-203` south, `A-204` west |
| `sections` | Two sections through the middle of the building (`ViewSection.CreateSection`): east-west, looking north; north-south, looking east. `CreateSection` looks along its box's `BasisZ`, its "view direction" (Revit's `View.ViewDirection`, "the direction towards the viewer", is the opposite), so since add-in 0.15.1 the box's `BasisZ` is the way the section looks, its `Min.Z` the cut through the middle and its `Max.Z` past the far half; add-in 0.15.0 took `BasisZ` for `View.ViewDirection`, and its sections looked the opposite way, cut at the far face. | `A-301`, `A-302` |
| `isometric` | One 3D view (`View3D.CreateIsometric`, turned as Revit's default 3D view), its section box the building's, the box's own lines hidden. | `A-401` |

- **North** is the model's own: its internal y axis, as Revit's project north. A building turned in its model is drawn square to the model's axes, not to its walls.
- **The building** is the extent of the model's walls, floors, roofs, ceilings, columns, structural framing and foundations, stairs, railings, doors, windows and generic models (their bounding boxes, in internal feet); every plan and elevation is cropped to it with a margin of 5% of its largest side, never less than 3 ft, its crop region hidden and its annotation cropped: a plan by its `View.CropBox`, in the view's own frame; since add-in 0.15.2 an elevation across only, in model coordinates, never through `View.CropBox`'s `Transform` (the second live run read east's and west's turned 45 degrees in plan, though each is drawn square-on, and north's region wholly south of the building). An elevation's view plane is the middle of the crop region Revit made (`View.GetCropRegionShapeManager().GetCropShape()`), taken only when its points lie in one plane square to `View.ViewDirection`; its crop is a rectangle on that plane along `View.RightDirection` and `View.UpDirection` holding the building and the margin, checked (`IsCropRegionShapeValid`) and set (`SetCropShape`) where the view's crop may take a shape (`CanHaveShape`); its crop box Z is not set. Since add-in 0.15.1 each elevation and section is then made to see past the building's far side: its far clipping turned on and its *Far Clip Offset* set to the depth it needs, to the building's far side and the margin, through its *Far Clip Active*, *Far Clipping* and *Far Clip Offset* parameters (`VIEWER_BOUND_ACTIVE_FAR`, `VIEWER_BOUND_FAR_CLIPPING`, `VIEWER_BOUND_OFFSET_FAR`), since setting a crop box alone left the first live run's north elevation short of the house: an elevation's from its view plane (since add-in 0.15.2, `DrawingSets.ElevationDepthFrom`; from its marker when no plane was read), a section's from its cut, or from Revit's own `View.Origin` where that is further. A model with none of those gets its plans and no elevation, section or 3D view, and the report says why.
- **Numbers and names**: a sheet number the model already holds, in any case, is skipped for the next free one of the same series, never reused; a series whose 99 numbers are all taken makes no sheet. Each view is named as its sheet (`Level 1 Floor Plan`, `North Elevation`, `East-West Section`, `3D View`), less the characters Revit forbids in a name, and given ` (2)`, ` (3)` ... where the model holds the name.
- **The title block**: the one `title_block` names (by family and type, as a wall type is named; one the model does not hold makes the change not applied, naming those it holds), else the first the model holds by family then type, else none (`ViewSheet.Create` with an invalid id). The report lists those the model holds (`title_blocks_held`).
- **The scale and the viewport**: the sheet's usable area is its title block's box on the sheet less a margin of 4% of its shorter side and, at its right, 18% of its width for the title strip; a sheet with no title block is laid out as ARCH D (36 x 24 in), or A1 (841 x 594 mm) in a metric model (the model's display units). The scale is the largest standard one at which the view fits that area (`View.Outline` read at Revit's scale, the scale set, the view measured again, since annotation does not scale with it): 1/4" = 1'-0", 3/16", 1/8", 3/32", 1/16", 1/32", 1/64", or 1 : 50, 100, 200, 500, 1000, 2000, 5000; a view with nothing in it takes 1/8" = 1'-0" or 1 : 100. Its viewport is placed at the area's middle (`Viewport.Create`) and fits when its box (`GetBoxOutline`, its label left out) lies within the area. These margins, the title strip and the default sheet are this add-in's own choices: a live run on a real title block is what tells whether they suit it.
- **The report**: the change's `drawing_set` gives the kinds asked, the title block and how it was chosen, the sheet's usable area, the building's extent, and per view its kind, its level, face or cut, which way Revit made it look (`looking`, from its `view_direction`), a section's cut plane and how far it stands from the middle, its view, sheet, title block, viewport and elevation marker by element id, its scale (`scale`, `scale_text`), its viewport's box on the sheet and whether it `fits`, and `why` it was not made, placed or fitted, or is not as asked; `totals.views_added` and `totals.sheets_added` count them. **How each elevation and section is read back** (since add-in 0.15.2): once everything is set and placed, `building_elements_seen` counts the building's elements Revit passes in the view (`FilteredElementCollector` over the view, the building's categories, no element type or view-specific element); a view that shows none says why ("Revit shows none of the building's 165 elements in it"), as does an elevation whose building stands behind its view plane. That proves a view empty, never whole: Revit's API reference says the collector may still pass an element outside a crop. Beside it, as Revit's readings and **not judged**: its far clip (`far_clip_active`, `far_clip_ft`), its crop box in model terms (`crop_min_ft`, `crop_max_ft`) and its `View.Origin` (`origin_ft`), with `depth_needed_ft` the depth the add-in set. Add-in 0.15.1 judged the far clip read back against the depth set and the crop through its frame; the second live run showed the *Far Clip Offset* reads back from `View.Origin`'s plane, not the view plane it was set from, and that judgement passed a north elevation that printed no house and failed three that print it. Each elevation also gives its view plane (`view_plane_ft`), its crop region read back (`crop_loop_ft`), and `readings`: Revit's `View.CropBox` and its frame, `View.Origin`, its right, up and view directions, its *Far Clip Offset* and its crop region, as made, cropped, far clipped and placed. The change is `applied` when every view asked (but a plan left out on the list's word) was made, placed and fits; `applied_in_part`, naming each that is not, when some view was made; and the report check holds the set to that (`DrawingSets.Problems`, run by `ReportCheck`).
- **It adds no building element**: the views and sheets are drawings of the model, not content of it, so a new model's first list needs more than a set (`NewModel.AddsSomething`), and nothing about it reaches the model's IFC.
- *Measured by the first live run* (2026-11-10, add-in 0.15.0, Autodesk's `rac_basic_sample_project.rvt`): each elevation marker's kept slot looked at its face; `CreateSection` looks along its box's `BasisZ`, the viewer and the cut at its `Min.Z` (its two sections' `View.ViewDirection` and `View.Origin`, to 0.001 ft), which 0.15.1 builds on. *By the second* (2026-11-11, add-in 0.15.1, the same model): the plans, the 3D view and both sections are right; the north elevation still printed no house, its region (`View.CropBox` through its `Transform`) wholly south of the building, its near face the north marker's y mirrored through `View.Origin`'s y; the *Far Clip Offset* read back is the distance from `View.Origin`'s plane to the far face, and the value set, measured from the near face, matched north and south; east's and west's `Transform` reads turned 45 degrees in plan while their `ViewDirection` reads (±1, 0, 0) and their sheets draw them square-on. 0.15.2 answers those. *Not established*: whether north's frame was mirrored when Revit made the view, or between 0.15.1's read of its crop box and its set; `readings` now separate the two. *Not yet run in cloud Revit*: the elevations' crops on their view planes (whether `GetCropShape`'s points are in model coordinates as read, and lie on the near face), their far clips from that plane, the count of what each view shows, the scales `View.Outline` leads to on other title blocks, and the PDF of sheets with no title block.

### Saving families out of the model (add-in 0.12.0)

The read-only probe can also save **loadable families** a person names out of the model as family files, so a family one model holds (a footing's, a pile's) can be loaded into another by an edit's `family_file` ([above](#foundations-change-list-version-4-add-in-0110)), as the owner settled it in flo2-rvt's design (`dec:the-probe-saves-families-a-person-names-as-rfa-files`). The model is never changed: the probe commits nothing and the job box closes it without saving, as before.

**The names.** `rvt_probe_start`'s `save_families` names 1 to 8 families, each once, by its family name exactly as the probe's report lists it (`types.*[].family`; case and spaces count). Each must be a name a family file may have, since a saved family is meant to be an edit's `family_file` and an edit loads a family under its file's name: `<name>.rfa` must match the change-list schema's `FamilyFile` (no `< > : " / \ | ? *` or control character, at most 200 characters before `.rfa`), and two names may not differ only in case (Windows, where cloud Revit saves them, holds them as one file name). A name that breaks either is refused by name before anything is asked of Autodesk, never renamed into a file that would load as another family.

**The handover.** Every probe hands the add-in the list as its input `saveFamilies`, `save-families.json`, in canonical form (`{"families":[...],"version":1}`, an empty list when it saves none), so no WorkItem ever leaves one of the probe Activity's inputs out. The job record (`workitem.json`) counts the names.

**What the add-in does with each name**, in order (`addin/src/Probe/FamilySave.cs`, `addin/src/Edit/Logic/FamilySaves.cs`): the one family the model holds under exactly that name (Revit's `Family` elements), when it is not in place and Revit lets it be edited, has its family document opened (`Document.EditFamily`, as the probe already opens foundation families to read their sizes), saved as `<name>.rfa` under the working folder's `families/` (the folder, and the name, an edit loads a family file from) with `Document.SaveAs` in the engine's own format, Revit 2024, and closed without saving again; it is copied to `family<n>.rfa`, n the name's place in the list asked, which Design Automation hands back as the probe Activity's optional output `family<n>`. Its sha256 is read from those bytes. Not saved, each with why: a name the model holds no family of (the report names one that differs only in case or end spaces), a **system family** (a wall foundation type's, a basic wall's: Revit holds its types in the model itself and never saves it as a family file), an in-place family, one Revit does not let be edited, two families of one name, a saved file of more than 32 MiB (33,554,432 bytes, the most an edit takes in one family file) or one that would take all a probe saves past 64 MiB (67,108,864 bytes), and one Revit will not save (its exception). The probe still succeeds.

**The report's `families_saved`**, present when names were asked: one entry for each name, in order, `{ family, was: "saved" | "not_saved", file?, output?, category?, types?, format?, bytes?, sha256?, why? }`. A saved one gives `file` (`<family>.rfa`), `output` (`family<n>.rfa`), its category and types (the first 200), `format` (the saved file's Revit release, from its header), `bytes` and `sha256`; one not saved gives `why` alone. The add-in checks the section against what it promises before it writes the report (`FamilySaves.Violations`), naming any break as a probe warning.

**The Activity's outputs.** `family1` to `family8` are each **optional**, and every probe's WorkItem names all eight, so a WorkItem never leaves one of the Activity's parameters out; a probe that saves fewer leaves the rest unwritten, as it leaves `sheets.pdf` unwritten for a model with no printable sheet. Two things say that is safe: Autodesk's WorkItem reference says that failing to find or upload an *optional* output argument is OK, and the first live probe (2026-10-31) and the first live probe of add-in 0.11.0 (2026-11-06) each left `sheets.pdf` unwritten on a model whose sheets are all placeholders and ended in `success` (flo2-rvt's design, `fact:the-first-live-probe-ran-in-108-seconds-and-its-outputs-wait-on-the-gateways-s3-host-check-2026-10-31`). One output per family, rather than one zip of them all, keeps each family a file the gateway saves as it is, with its own size and sha256, with nothing to unpack on flo2.io. *Not yet run in cloud Revit*: that `Document.SaveAs` saves a family document `EditFamily` opened in Design Automation (`EditFamily` itself is measured: the 0.11.0 probe of 2026-11-06 opened every Structural Foundations family of a real model), that the saved file loads in an edit of another model, and that `BasicFileInfo.Extract` reads a saved family's format.

### New levels (change-list version 5, add-in 0.13.0)

**`add_level`** adds a level by `name` at an `elevation`, `relative_to` the project origin (Revit's `Level.ProjectElevation`) or its own Elevation Base (`Level.Elevation`), as `set_level_elevation` measures one, in its own transaction. Its name must be one no level of the model holds, exactly (case and spaces count, as `level_name` matches); one that does is not applied, naming the model's levels, and one Revit refuses for its own rules rolls the change back with Revit's words. No two `add_level` changes of one list may name the same new level (all three checks refuse it). The add-in makes it with `Level.Create`, names it, sets its Elevation so that it stands where the change asked (ProjectElevation is read-only and differs from Elevation by a fixed offset, so a target from the origin moves Elevation by the same amount), and sets its Building Story setting on where Revit holds it off: Revit's IFC exporter writes an `IfcBuildingStorey` for every level whose setting is on or absent, with or without a plan view (revit-ifc `Release_24.x.x`, commit `887c3d3e`: `Utility/LevelUtil.cs` `IsBuildingStory`, `Exporter/Exporter.cs`). **No plan view is made**: the change makes a datum and nothing else; a person adds plans of it in Revit as of any level. Later changes of the same list place walls, floors, rooms, doors and foundations on it by its name (`level_name`; its storey's GlobalId is not known until the job's report). The report names it under `added` as `new_level`: its element id, the GlobalId of the storey Revit's IFC export writes for it (`ExporterIFCUtils.CreateAlternateGUID`, as every level is named; also the element's `global_id`), its elevation both ways as Revit holds it beside the elevation asked, whether it is a building storey, and its level type's Elevation Base. A level not named as asked, not where it was asked, not a building storey or with no storey GlobalId reads `applied_in_part`, saying which (`addin/src/Edit/Logic/NewLevels.cs`). flo2.io requires its elevation, as a wall's height, to come from the calc record an edit names (`numbers_from`).

### A new model (add-in 0.13.0)

`rvt_new_model_start` makes a model the design does not have, and fills it with its first change list, in **one job**, as the owner settled it in flo2-rvt's design (`dec:a-new-model-is-made-and-filled-in-one-job`, `dec:a-new-revit-model-starts-from-revits-own-no-template-project-or-a-template-file-the-design-keeps`).

**What it starts from**, exactly one of:
- `units`, `imperial` or `metric`: **Revit's own project with no template** (`Application.NewProjectDocument(UnitSystem)`). No file is needed. Its levels and types are Revit's defaults, few of them, and no door or foundation family: the report lists them (`new_model.levels_at_start`, `types`), and families come in through `family_file` (a footing's or pile's, and since change-list version 6 a door's) and a probe's saved families. *Unproven until the first run*: what that project holds.
- `template_file`, a **Revit project template** (`.rte`, saved by Revit 2024 or older) the design keeps, by its file name: flo2.io hands it over as it hands a family file (the hidden context's `template`), and the add-in makes the project from it (`NewProjectDocument(path)`). Its levels, types, views and units are the new model's.

**Design Automation.** The job has its own Activity, `Flo2RvtNew`, over the one AppBundle, with **no model input**: `newModel` (`new-model.json`, what it starts from, required), `template` (`template.rte`, optional, named only when it starts from one), `changes` (`changes.json`, required) and `family1` to `family8` (optional), and an edit's outputs. A separate Activity, rather than the edit's with its model left out: the edit Activity's model input stays required, so Design Automation fails an edit that lost its model before Revit starts, and an edit never quietly becomes a new model; the add-in tells the jobs apart by the files each Activity hands over (`addin/src/Edit/Logic/JobSelection.cs`). **The template is a plain input** that the add-in opens itself, by its `localName`: no Activity's command line has `/i`, so the engine never opens it. Autodesk's APS blog (Xiaodong Liang, 2019-03-20, [When working with NewProjectDocument by Automation API](https://aps.autodesk.com/blog/when-working-newprojectdocument-design-automation-api)) found a template handed over as the `/i` input opened and locked by Design Automation's sandbox, so that `NewProjectDocument` threw, and defined it as a common parameter instead, as here. Autodesk's Design Automation troubleshooting page, read 2026-11-06, still says to leave `/i` out and open the file in the add-in by a fixed `localName`; neither it nor any page of the developer's guide names a template that Design Automation ships, and none is assumed.

**What the job does**: the job box makes the project (`addin/src/Jobs/JobBox.cs`, the one place a model is opened or made, which closes it without saving), then the edit job fills it exactly as it edits a model: the family files the list names are loaded, the changes run in order, each in its own transaction, and when at least one was kept, the IFC is exported and the model saved once as `model.rvt` through the one save path. **A list that adds nothing is refused** (no `add_level`, `add_wall`, `add_floor`, `add_room`, `add_door`, `add_footing`, `add_wall_footing` or `add_pile`): an empty model is not a result anyone asked for. A change naming a type the new model does not hold is not applied on its own, naming the types it does hold, as in any edit. When Revit makes no model (a template it cannot read, one saved by a later Revit), the job still writes `report.json`, refused with why, and saves and exports nothing.

**The report** is an edit's, with `new_model` (`from`, `units` or `template`: its name, bytes, sha256 and format; `created`, and `error` when not; `seconds`; `levels_at_start`) and `types`, every wall, floor, door and foundation type the new model holds after the list, as the probe lists a model's, so the next edit can name them; they are listed even when no change was kept. Its `file` section is the saved `model.rvt`'s header.

**Coordinates.** In a new model, shared coordinates are its internal ones, unless its template sets them otherwise (the report's `coordinates` say which), and Revit's IFC export of it is written in them. So the first list's points go in as `internal` (or `shared`, the same there), and later edits take theirs from the new model's own IFC as for any model. To rebuild a draft from another IFC, use its local coordinates (its placements in its own length unit, not map coordinates its georeferencing gives: Revit keeps a model within 20 miles of its internal origin); no change kind sets the new model's survey point or true north yet.

### How an IFC GlobalId maps to a Revit element

As Autodesk's open-source IFC exporter for Revit maps them ([revit-ifc](https://github.com/Autodesk/revit-ifc), branch `Release_24.x.x` at commit `887c3d3e`, `GUIDUtil.cs`), with its default options (the probe's and the edit's exports use them):
- **An element's GlobalId** is its `IfcGUID` parameter (`BuiltInParameter.IFC_GUID`; `IFC_TYPE_GUID` for a type) when that holds a valid IFC GUID and the element is not a curtain wall; otherwise Revit's export id for it, `ExportUtils.GetExportId(document, id)`, compressed to IFC's 22-character form (`addin/src/Edit/Logic/IfcGuid.cs`). An `IfcGUID` value is set when the model was imported from IFC or exported with "store the IFC GUID" on.
- **A level's storey GlobalId** is `ExporterIFCUtils.CreateAlternateGUID(level)`.
- The add-in indexes every element this way **before** any change runs. A GlobalId matches the element that has it as its exported GlobalId first; failing that, an element whose export id or `IfcGUID` value it is (an IFC exported with other settings); two elements either way is refused as ambiguous (Revit copies the `IfcGUID` parameter with a copied element, and the exporter then gives the copy a fresh GlobalId, in an order the add-in cannot know).
- What the exporter writes that is not an element (openings, the parts of a split wall, a curtain wall's sub-elements, the project, site and building) matches nothing, and is reported as not found.

### A failed change rolls back alone

Revit's failure processing is answered by the add-in, never by a person: every message is recorded in `revit_messages`. **A warning is dismissed and the change is kept. An error rolls the whole change back**, with no default resolution chosen on anyone's behalf (Revit's resolutions for errors are edits of their own, such as "delete the element", that the list did not ask for); so does an exception from the Revit API. Then the job goes on to the next change. The exceptions are a level move whose change says `groups_in_the_way: "ungroup"` or `constraints_in_the_way: "remove"`: rolled back for groups or constraints in the way alone, it is tried again, in a transaction of its own, with only the groups Revit named ungrouped and the constraints it named removed first (above); the person approved that edit when they approved the list. A drawing set's views and sheets (since add-in 0.15.0) are each a part of its change, in a sub-transaction: an exception from the Revit API in one rolls back that part alone, and the set's report says why; an error Revit raises at the change's commit still rolls the whole set back. Each change's `status` is `applied`, `applied_in_part`, `rolled_back` or `not_applied`; the list's `outcome` is `all_applied`, `partly_applied`, `none_applied`, or `refused` when the list itself could not be read. The model is exported and saved when at least one change was kept, and not otherwise.

This was chosen over stopping at the first failure because a list is approved as a set of independent edits, each reported on its own, and the input is never changed: a later change that depended on a failed one says so itself (its level or elements are not found). Changes that must stand or fall together go in a list of their own, whose `outcome` then says whether all of them were applied.

### How the result is saved

The job box opens a workshared input **detached from its central, with its worksets preserved** (the probe's `report.json` showed `is_workshared: true, opened_detached: true` for such a model). The edit then saves it once, as a new file, `model.rvt` (`addin/src/Edit/SaveResult.cs`):
- **Workshared input: saved as a new central model**, with `WorksharingSaveAsOptions.SaveAsCentral = true`, then `WorksharingUtils.RelinquishOwnership` of everything, and the report lists each user workset and who Revit says owns it after the save.
- **Not workshared: saved as a plain file**, with no worksharing options.

Verified against Autodesk's documentation: Revit 2024's [`Document.SaveAs(String, SaveAsOptions)`](https://rvtdocs.com/2024/df74c7e1-a98a-7751-676a-e9b074566f62) refuses a document that "was opened detached" unless `WorksharingSaveAsOptions.SaveAsCentral` is true, and refuses worksharing options on a document that is not workshared; the 2024 API's own notes for `SaveAsCentral` say the same; Autodesk's post on [worksharing in Design Automation for Revit](https://aps.autodesk.com/blog/worksharing-model-support-revit-design-automation-0) (2020) gives the same recipe (save as central, relinquish), and says Design Automation opens workshared models detached with their worksets preserved. Assumed until the first live edit: that the save and the relinquish behave on Design Automation as they do in desktop Revit, and what the architect sees on opening it. A file-based central keeps its incremental backups and ownership in a backup folder beside it (the 2024 API's notes on `SaveAsOptions.MaximumBackups`), which is not part of the output; the architect opens `model.rvt` the way any workshared model received from outside the office is opened: detached, saved as their own new central.

## The add-in

`addin/` is a Revit 2024 add-in for the Automation API (C#, .NET Framework 4.8): an `IExternalDBApplication` that answers `DesignAutomationBridge.DesignAutomationReadyEvent`, packaged as an AppBundle zip (`Flo2RvtProbe.bundle/PackageContents.xml`, `Contents/Flo2RvtProbe.addin`, `Contents/Flo2RvtProbe.dll`).

- A small job registry (Autodesk's registered-tool pattern from aps-sample-revit-mcp-tools-bundle) holds three jobs, `probe`, `edit` and, since add-in 0.13.0, `new`. The working folder says which runs: `new-model.json`, the new-model Activity's required input, means a new model; `changes.json` alone, the edit Activity's required input, means the edit (`addin/src/Edit/Logic/JobSelection.cs`). The probe Activity has no parameter that could put either there, and the edit Activity none that could put `new-model.json`.
- The job box opens `input.rvt` from the working folder itself (detached from its central, all worksets open, when the file is workshared), runs the job, and **closes the input without saving**. The edit writes its result as a new file before that, through its one save path.
- The probe reads the levels, sheets, links, element counts, versions and stored warnings; prints the sheets with `Document.Export` and `PDFExportOptions` (`Combine`); exports IFC with `IFCExportOptions` (`IFC4DTV`, `ExportBaseQuantities`); and writes `report.json` last, recording any export that failed. Each export runs inside a transaction that is **rolled back**: Revit requires an open transaction for IFC export. The probe commits nothing. Since add-in 0.11.0 it also opens each foundation family's own document (`Document.EditFamily`, at most 100 families) to read the instance parameters the family defines and which parameters a formula sets, and closes it without saving; a family it cannot open is listed with why (`instance_sizes_unread`).
- Since add-in 0.11.0 the edit Activity also hands over up to eight family files, `family1.rfa` to `family8.rfa`, in the order the change list first names them (`addin/src/Edit/Logic/Foundations.cs`, `FamilyFiles`); the edit copies each to its own name under `families/` and loads it before any change runs, each load a transaction of its own through `ChangeRunner`. Since add-in 0.14.0 a door's comes the same way, and each is held to the category its changes need (Doors, or Structural Foundations); the new-model job loads them on the same path.
- The edit runs each change through `addin/src/Edit/ChangeRunner.cs`, the only file that commits a transaction (since add-in 0.15.0 also the sub-transactions a drawing set's views and sheets each run in, `ChangeRunner.Part`, which Revit commits only with the change's own), and saves through `addin/src/Edit/SaveResult.cs`, the only file that saves a model, with exactly one `SaveAs`. Since add-in 0.12.0 the probe saves the families it is asked to through `addin/src/Probe/FamilySave.cs`, the only file that saves a family document, with exactly one `SaveAs`, on the document `Document.EditFamily` opened, which it closes with `Close(false)`. CI runs `scripts/addin-save-guard.ts` before the build: it fails if any other file commits, saves, synchronizes or relinquishes, if the save path holds more than one `SaveAs` or commits, if the family save holds more than one `SaveAs`, saves anything but a document `EditFamily` opened, leaves it unclosed or saves another way, if the probe's files name the edit's, or, since add-in 0.13.0, if a new project document (`NewProjectDocument`) is made anywhere but `addin/src/Jobs/JobBox.cs`, or the job box closes a model other than with `Close(false)`.
- A heartbeat writes to the job log every 20 seconds, so a long open or export is not taken for an idle job.
- It builds against reference assemblies from NuGet, on any OS: `Nice3point.Revit.Api.RevitAPI` 2024.3.60 (MIT packaging of Autodesk's reference assembly), `Autodesk.Forge.DesignAutomation.Revit` 2024.0.2 (Autodesk's bridge) and `Microsoft.NETFramework.ReferenceAssemblies.net48`. None is shipped in the bundle; the engine provides them.

The probe ran live once, on 2026-10-31 (108 s), and the edit (0.2.0) once, the same day, on Autodesk's sample model (108 s). That first edit's report said 44 elements could not be deleted that Revit had deleted with their curtain walls, left three elements on the emptied level unreported, and named 15 deleted internal elements by nothing: 0.3.0 reconciles every change with the model after it, lists what is left, takes Schedule-Level elements, and names every element by its Revit class. 0.3.0's re-run of that edit, the same day, counted 14 parts of kept elements as left on the emptied level beside its 2 real leftovers: 0.4.0 ties an element to a storey only when Revit's IFC exporter exports it on its own, and lists each part under its owner. `addin/tests` runs the first edit's c3, from its element ids and GlobalIds, and the re-run's c3, from its element ids, Revit classes and categories, through the add-in's logic, and checks the report's invariants (`addin/src/Edit/Logic/ReportCheck.cs`), which the edit job also checks on every change before it writes `report.json`. CI proves the add-in compiles, that the bundle has the expected layout, and that its pure logic passes `addin/tests`.

**Every element the report names**, the add-in indexed before any change ran (`addin/src/Edit/ElementIndex.cs`): its GlobalId, category, Revit class (`Element.GetType().Name`) and whether it is a model element. Revit's collectors do not list every element (the first live edit deleted 15 that none had listed), so after them the index asks Revit for every element id up to the highest listed one, plus a margin, for 60 s at most; `edit.index` in the report says how many it found that way and how far it got.

## Running the server

```sh
npm ci --omit=dev
FLO2_RVT_LOCAL_TOKEN=… FLO2_RVT_PORT=8740 node server/src/index.ts
```

`FLO2_RVT_BUNDLE` names the AppBundle zip a setup uploads (default `addin/dist/Flo2RvtProbe.bundle.zip` in the checkout), with its sha256 in `<zip>.sha256` beside it, as `sha256sum` writes it. On flo2.io, flo2.io's install (`ops/flo2-rvt-install` in the flo2 repository) puts there the zip this commit's CI built (the `Flo2RvtProbe.bundle` artifact of the CI run on the pinned commit), checked against the sha256 flo2.io pins for that commit; nothing on flo2.io builds the add-in. The server reads and hashes the zip again at every setup. Without it, jobs run as before and a setup is refused, saying why; the start log says which (`bundle_ready` or `bundle_absent`).

Node 22.18 or later runs the TypeScript directly. On flo2.io it runs as its own service under its own unprivileged user, with network reach and no access to design files on disk. It logs one JSON line per event to stderr, never a token, a signed URL or a file's contents.

## Setting up a person's Autodesk app

A person creates their own Autodesk app once (step 1 below) and enters its keys on flo2.io (flo2.io/account, Cloud Revit). **Nothing is run on their computer.** The first time a job is asked for on an app that is not set up, flo2.io says so and offers flo2-rvt's one-time setup; the person approves it on flo2.io the way they approve a job, told what it does, and it is recorded in their design like a job. flo2.io's gateway then calls `rvt_setup_run` with a token from the keys it already holds for that person's jobs, and flo2-rvt's server runs the registration below (`server/src/aps/registration.ts`, the same code as the command line) with the AppBundle it holds. It runs again, the same way, when a new flo2-rvt brings a new add-in version.

The command line (`npx flo2-rvt register`, step 3) stays, for an owner who runs flo2-rvt with their own keys rather than through flo2.io, and for developers.

1. **Create the Autodesk app** (Autodesk's [Create an App](https://aps.autodesk.com/en/docs/oauth/v2/tutorials/create-app/) walkthrough):
   1. Sign in at [aps.autodesk.com](https://aps.autodesk.com) (create an account if needed).
   2. Have a developer hub: with an APS plan, create one at [manage.autodesk.com](https://manage.autodesk.com) under Products and Services > Hubs > Create hub > APS developer hub. The Automation API is a paid API; check the plan's caps and the current price.
   3. Profile menu > **My applications** > choose the hub > **Create application**. Name it, choose the **Server-to-Server App** type (client credentials, two-legged tokens), and under **API Access** select the **Automation API** and the **Data Management API** (for its storage). Save.
   4. Copy the Client ID and Client Secret into your environment as `APS_CLIENT_ID` and `APS_CLIENT_SECRET`, and into flo2.io's encrypted store as flo2.io asks. Never put them in a file in this repository.
2. **Get the AppBundle**: download `Flo2RvtProbe.bundle` from the CI run's artifacts, or build it: `dotnet build addin -c Release` writes `addin/dist/Flo2RvtProbe.bundle.zip`.
3. **Register** (flo2.io does this from its server once the person approves it; by hand, on your own machine, once, and again for a new add-in version; since add-in 0.13.0 it registers the new-model Activity too):

   ```sh
   npm ci
   APS_MONTHLY_HOURS=2 npx flo2-rvt register --bundle addin/dist/Flo2RvtProbe.bundle.zip
   ```

   For a new add-in (such as 0.2.0, which adds the edit, 0.3.0 or 0.4.0), run the same command with the new bundle: it adds a version of the AppBundle, a version of the probe Activity, creates the edit Activity (or a version of it), and moves every `prod` alias. The nickname and the cap are kept.

   In this order:
   1. **The owner prefix, first.** A nickname the app already has is kept. An app with none is named by its client id (`<client id>.Flo2RvtProbe+prod`), which Autodesk always accepts: **no nickname is ever derived or set for you.** A nickname must be unique across all of Autodesk, Autodesk lets an app take one only while it has no AppBundle or Activity ([Task 3, Create a Nickname](https://aps.autodesk.com/en/docs/design-automation/v3/tutorials/revit/step3-create-nickname/)), and its 409 does not say which of the two refused it; flo2-rvt 0.5.0 derived one from the client id, and a person's first setup stopped on that 409. Only when you name one yourself with `APS_NICKNAME` (letters, digits and underscores) does the command line send `PATCH /forgeapps/me`, on an app with no data; one Autodesk refuses stops the run before anything is created, with Autodesk's status and words. An app that already has data and no nickname carries on with its client id: setting one then would need `DELETE /forgeapps/me`, which deletes everything on the app, and this command never calls it.
   2. The AppBundle, uploaded as a new AppBundle or a new version of it, and its `prod` alias. One AppBundle, `Flo2RvtProbe`, carries both jobs.
   3. The `Flo2RvtProbe`, `Flo2RvtEdit` and `Flo2RvtNew` Activities on the `Autodesk.Revit+2024` engine, named `<owner>.Flo2RvtProbe+prod`, `<owner>.Flo2RvtEdit+prod` and `<owner>.Flo2RvtNew+prod`, each with its `prod` alias. The probe Activity takes the model (`rvtFile`, `input.rvt`) and, since add-in 0.12.0, the families to save (`saveFamilies`, `save-families.json`, required), and puts `report.json` (required), `sheets.pdf`, `model.ifc` and `family1` to `family8` (`family1.rfa` ..., each optional). The edit Activity takes the model (`rvtFile`, `input.rvt`) and the change list (`changes`, `changes.json`, required), and puts `report.json` (required), `model.rvt`, `sheets.pdf` and `model.ifc` (each optional). Since add-in 0.13.0 the new-model Activity takes no model: what it starts from (`newModel`, `new-model.json`, required), its template (`template`, `template.rte`, optional), the change list (`changes`, required) and up to eight family files (optional), and puts what the edit puts.
   4. Autodesk's own monthly processing cap on the app (`frontendLimits.limitMonthlyProcessingTimeInHours`, `APS_MONTHLY_HOURS`, default 2), read back.

   It prints the owner prefix and how it was settled, each version and alias, and the cap Autodesk reports. flo2-rvt's server reads the same prefix from `GET /forgeapps/me` for every job. It sends GET, POST, PATCH and PUT, never DELETE. From flo2.io, the cap is the person's own flo2.io monthly limit in whole hours, rounded up, and no nickname is set: a nickname the app has is kept, and an app with none is named by its client id.
4. **Check the engines** whenever the monthly check asks: `npx flo2-rvt engines` lists Design Automation's Revit engines beside the dates Autodesk's Engine Lifecycle Policy page gives. The Revit 2024 engine takes no new AppBundles or Activities after **2027-03-29** and is removed on 2029-03-29.

## Development

```sh
npm ci
npm run lint && npm run typecheck && npm run gen:check && npm test
node scripts/addin-save-guard.ts   # the add-in commits and saves only on the edit job's one path
dotnet build addin -c Release      # the .NET SDK (10.0) builds the net48 add-in on Linux too
dotnet run --project addin/tests/Flo2RvtLogic.Tests.csproj -c Release   # the add-in's pure logic, on .NET 10
```

The tests cost nothing and touch no network: Autodesk is a loopback stand-in that answers with responses recorded from Autodesk's own services (`server/test/fixtures/autodesk/`, each naming its source), and the monthly check's tests replay recorded GitHub, NuGet, npm and documentation responses. Test data uses Autodesk's public sample model's name and made-up values, and, for the first live edit's change c3, the element ids and GlobalIds of that sample's elements (`addin/tests/fixtures/`).

## Monthly checks

`.github/workflows/dependencies.yml`, on the first of each month and on demand:

- **currency** (`scripts/dependency-currency.ts`): every npm and NuGet pin and GitHub Action against its latest release, and the Revit engine against its deprecation date. A newer major fails unless `dependency-holds.json` holds it back with a reason and a date to look again.
- **autodesk** (`scripts/autodesk-watch.ts`, `watch/autodesk.json`): Autodesk's repositories (pinned by commit), Autodesk's Design Automation and APS SDK packages, and the documentation of the Automation API, sign-in and storage, read as data the way Autodesk's own aps-docs-portal skill does. When anything moved it opens one issue: the commits since each pin, the version changes, the pages added, removed or changed (portal links from the contents files), new Change History entries in full, and the Revit engine dates, with links to the [HTTP reference](https://aps.autodesk.com/en/docs/design-automation/v3/reference/http/) and [developer's guide](https://aps.autodesk.com/en/docs/design-automation/v3/developers_guide/overview/). Read it, then move the pins with `npm run watch:autodesk -- --update` in a pull request.

## Privacy

This repository is public. It never names or holds a person's model, building, address, architect or family, nor their files, reports or job outputs. Tests and examples use Autodesk's public sample model (`rac_basic_sample_project.rvt`) and made-up names. A person's files live only in their own flo2 design.
