# Changelog

## 0.5.0 (unreleased)

flo2-rvt sets itself up on a person's own Autodesk app from flo2.io, and a job checks the app first. A person's first edit job (2026-11-01) made a bucket on their own Autodesk app and uploaded their model and its change list, and then Autodesk refused the WorkItem with HTTP 400, "The activity <client id>.Flo2RvtEdit+prod could not be found (Parameter 'activityId')": flo2-rvt had never been registered on that app. Registration was a terminal step on a person's own computer, and nothing checked it before a job. Contract v3 (v2, and the setup; nothing of v2 changed). The add-in is unchanged (0.4.0); the change-list schema stays version 0.

- **The setup, from the server** (`rvt_setup_run`): the owner's registration (moved to `server/src/aps/registration.ts`; `scripts/lib/registration.ts` re-exports it for the command line), run on the person's app with the job token flo2.io mints from the keys it already holds, once the person has approved it on flo2.io. The hidden context's new `setup` carries what they approved: the monthly cap in whole hours, and the sha256 of the AppBundle they were shown. The AppBundle is the zip CI built for this commit, which flo2.io's install puts beside the server with its sha256 checked (`FLO2_RVT_BUNDLE`, default `addin/dist/Flo2RvtProbe.bundle.zip`, and `<zip>.sha256`); the server reads and hashes it again at each setup and refuses, asking Autodesk nothing, when it is absent, does not match its sha256, or is not the one approved. Then the nickname (on an app with no nickname and no data), the AppBundle and its prod alias, both Activities and their prod aliases, and Autodesk's monthly cap, read back. GET, POST, PATCH and PUT only, never DELETE.
- **The check** (`rvt_setup_check`, read-only): `GET forgeapps/me`, the AppBundle and each Activity the job needs by their qualified ids (`activities-id-GET`, `appbundles-id-GET`): `ready`, `not_set_up` or `outdated`, what was found, and with `plan` what a setup would do there. Every AppBundle and Activity description now ends with `(flo2-rvt add-in <version>)`, the add-in's own version (`ADDIN_VERSION`, held equal to the csproj's by a test), which the check reads back; an app registered by 0.4.0 or earlier names none, and reads `outdated` until its next setup. Assumed until the first live setup: that Autodesk returns the description as it was given.
- **A start reads its Activity first**: `rvt_probe_start` and `rvt_edit_start` read the job's Activity on the person's app before they make a bucket or upload anything; an app that does not hold it is refused in plain words: not set up, nothing uploaded, nothing ran, nothing billed, and to ask flo2.io for the one-time setup and start the job again.
- **Autodesk's activity-not-found, in plain words**: a WorkItem refused with 400 or 404 naming a missing Activity or AppBundle says the same, with Autodesk's own words quoted after. Both refusals carry `_meta["flo2.io/error"] = {code: "not_set_up", billed: false, autodesk_said?}`, so the gateway acts on the case. A 401 or 403 reading the app's nickname says the app may lack the Automation API.
- **After a setup the next job runs at once**: the server keeps the nickname a setup set, and forgets one a refused start read.
- **CI**: the `Flo2RvtProbe.bundle` artifact carries `Flo2RvtProbe.bundle.zip.sha256` beside the zip, and the run's summary names the sha256.
- **Tests**: the 400 path (Autodesk's recorded answer of 2026-11-01, on the stand-in), a start on an app never set up (no bucket, no upload, no WorkItem), the check on an app set up, never set up, and set up by an older flo2-rvt, and the setup's refusals and its run, after which the job that was refused starts. The first two failed on 0.4.0, the first with the very words that reached the person.

## 0.4.0 (unreleased)

A part goes with its owner. flo2-rvt 0.3.0's re-run of the first live edit (2026-10-31, Autodesk's sample model) listed 16 model elements as left on the emptied Level 2, all "tied_by ifc_storey": the 2 wardrobes, placed on no level, and 14 parts of elements the change keeps because they only reach Level 2 from below (four stair sketch boundary lines, seven rail path extension lines, a top rail, two curtain grid lines). The job's own IFC filed none of the 14 under Level 2, and the change read `applied_in_part` because of them. The add-in mirrored the exporter's storey rule, but not which elements it exports. Report version 2 still (fields added, none changed); contract v2 (the summary is unchanged); the change-list schema stays version 0.

- **The exporter's export filter, mirrored** (`addin/src/Edit/Logic/ExportFilter.cs`, read in Revit by `ExportReader` in `addin/src/Edit/Leftovers.cs`), from Autodesk's revit-ifc at the commit the storey rule cites: its collector (`ElementFilteringUtil.GetClassFilter`, `GetDesignOptionFilter`, `GetPhaseStatusFilter`), the Export to IFC setting (`ShouldElementBeExported`), and its class exporters (`CurveElementExporter.ShouldCurveElementBeExported`, `FamilyInstanceExporter.ExportFamilyInstanceElement`'s curtain-host test, `RailingExporter.CollectSubElements`). `tied_by: ifc_storey` is claimed only for an element the exporter exports as a product of its own; one it does not is tied by `storey_rule`. Where the rule cannot tell, the element is taken as exported and listed as left.
- **Parts go to their owner**: a sketch's curves to the sketch's owner (`Sketch.OwnerId`), a top rail, handrail or support to its railing, a curtain grid line, mullion or panel to its curtain wall, roof or system, an opening to its host. A part whose owner is still in the model is listed under it in the new `left_on_level.parts_of_kept_elements` (the owner's element id, GlobalId, category, Revit class, `exists`, `found_by`), and is not left. A part whose owner is gone is an orphan: in `elements`, `reason: orphaned_part`, with the gone `owner`, and counted. What the exporter does not export, names no owner, and no Revit setting ties is listed in the new `left_on_level.not_exported` with the exporter's reason, and not counted. Each listed part carries `part_of` (sketch, railing, curtain_grid, curtain_host, cut_host).
- **Only what is left counts**: `left_on_level`'s `total`, `model_elements` and `elements`, and `totals.elements_left_on_level`, hold what is left (exported standalone elements, orphans and the rest as before); only a model element among them makes the change `applied_in_part`.
- **Invariants**: `ReportCheck` also checks that a part is listed under one owner still in the model and not deleted, is neither deleted nor among what is left, and that an orphan's owner is gone.
- **Tests**: `addin/tests` runs the re-run's c3 (`addin/tests/fixtures/rerun-2026-10-31-c3-left-on-level.json`, element ids, Revit classes and categories only): the wardrobes stay the only model elements left, the 14 are listed apart, under their owners when Revit names them; a gone owner makes its parts orphans. The test failed on 0.3.0.

## 0.3.0 (unreleased)

The edit report, reconciled with the model after each change. flo2-rvt 0.2.0's first live edit (2026-10-31, Autodesk's sample model) said 44 elements could not be deleted that Revit had deleted with their curtain walls (and so read `applied_in_part`), left three elements on the emptied Level 2 that it did not name, and named 15 deleted internal elements by nothing at all. Report version 2; contract v2; the change-list schema stays version 0.

- **Reconciled**: what a delete refused before its transaction (`DocumentValidation.CanDeleteElement`) is judged against what the transaction deleted. Deleted with its host, it moves to the new `deleted_with_host`; only what is still in the model stays in `could_not`. The status and `why` follow from what is really left (`addin/src/Edit/Logic/Reconcile.cs`), for both delete kinds.
- **`left_on_level`**, for `delete_elements_on_level`, read from the model after the transaction: every element still tied to the level, with what ties it and why it was not taken: by its Revit settings, or by the storey Revit's own IFC exporter files it under (an element with no Revit level, by its height; one on a level that is not a building storey), the exporter's rule taken from Autodesk's revit-ifc at the commit the GlobalId mapping cites (`addin/src/Edit/Logic/Storeys.cs`, `addin/src/Edit/Leftovers.cs`). Nothing is deleted by a guess. The change reads `applied_in_part` only when a model element is left.
- **Schedule Level is taken**: `delete_elements_on_level` deletes a family instance whose Schedule Level (`INSTANCE_SCHEDULE_ONLY_LEVEL_PARAM`) is the level, as a person reading "everything on Level 2" means it. The schema's description, the README and the server's tool description say so.
- **Every element by its Revit class**: the element index records each element's class (`Element.GetType().Name`) and whether it is a model element before any change runs, and now also finds, by id, the elements Revit's collectors do not list (`edit.index` says how many). Every element in the report carries `revit_class` and `model_element`; every set counts `model_elements` apart from `other_elements`, with `by_class`; in `totals`, `elements_deleted` (and the other element counts) count model elements, with `other_*` counts beside them, and `elements_deleted_with_host`, `elements_could_not`, `elements_left_on_level`.
- **Invariants checked**: `addin/src/Edit/Logic/ReportCheck.cs` (no element both still in the model and deleted; a status that agrees with what is left; counts that add up). The edit job checks every change before it writes the report and records a break as a job warning; `addin/tests` runs the first live edit's c3 through the add-in's logic (`addin/tests/fixtures/live-edit-2026-10-31-c3.json`, element ids and GlobalIds only), a test that failed on 0.2.0.
- **Server**: the edit's report summary adds `other_elements_deleted`, `deleted_with_host` and `left_on_level`, and reads a 0.2.0 report as before (contract v2: nothing else changed).

## 0.2.0 (unreleased)

The edit job: real Revit 2024 applies a change list to a model and saves the result as a new model. Contract v1 (v0 plus the edit; nothing of v0 changed).

- **Server**: `rvt_edit_start` (`file`, `change_list`, `max_minutes`). The change list is checked against the one schema, read from its file through zod's `fromJSONSchema`, and the limits the add-in holds (512 KiB canonical, 20,000 GlobalIds, Revit's model extent), uploaded beside the model as `changes.json` in its canonical form (keys sorted, no whitespace), and named in the start result by its SHA-256. The WorkItem names `<nickname>.Flo2RvtEdit+prod`; the job record says which job it is, so `rvt_job_status` lists an edit's outputs (`report.json`, `model.rvt`, `sheets.pdf`, `model.ifc`; an optional one not written is left off) and summarizes its report (outcome, changes applied, applied in part, rolled back, not applied, elements deleted, model saved), after a restart too. A job record written before this version reads as a probe's.
- **Add-in**: the `edit` job beside `probe`, chosen by the working folder (`changes.json` means the edit). The three change kinds, with their semantics stated in the README (what "on a level" is, how a GlobalId maps to an element as Revit's IFC exporter maps them, what moves with a level); each change in its own transaction, a failed one rolled back alone; warnings dismissed and recorded, errors rolling the change back; what Revit deleted, modified and added on its own recorded per change; the edited model exported (IFC, sheets) and saved once as a new `model.rvt`, a new central model with its worksets when the input is workshared; `report.json` last. A new compile-time reference, `Nice3point.Revit.Api.RevitAPIIFC` 2024.3.60, for a level's storey GlobalId.
- **Logic tests**: `addin/tests`, on .NET 10, for the add-in's pure logic (GlobalIds, lengths, the change-list check on the shared cases in `schema/test/change-lists.json`, outcomes, `report.json`'s shape).
- **CI guard**: `scripts/addin-save-guard.ts` takes over from v0's grep: the probe still commits and saves nothing, and only `Edit/ChangeRunner.cs` commits and only `Edit/SaveResult.cs` saves, once.
- **Registration**: one AppBundle version for both jobs, the probe Activity's new version, and the edit Activity with its `prod` alias.
- **Schema**: the same version 0 and the same lists; its descriptions now state each change kind's exact meaning.

## 0.1.0 (unreleased)

The first version: a read-only probe.

- **Server** (`server/`): an MCP server on the MCP TypeScript SDK v2.4.0, Streamable HTTP on `127.0.0.1:8740` behind a local bearer token, with the two contract tools `rvt_probe_start` and `rvt_job_status`. It refuses calls without flo2.io's hidden job context and uses only the short-lived token that context carries.
- **Design Automation client**: the person's transient OSS bucket, a streamed, chunked upload through signed S3 URLs that completes only when the bytes match the stated size and SHA-256, WorkItems with `limitProcessingTimeSec` and OSS object URNs, status reads, and signed download URLs for the outputs.
- **Change-list schema** (`schema/change-list.schema.json`): version 0, the element reference and three change kinds, with TypeScript and C# types generated from it. No edit job runs them yet.
- **Add-in** (`addin/`): a Revit 2024 add-in for the Automation API that opens the model, changes nothing, and writes `report.json`, `sheets.pdf` and `model.ifc`; packaged as an AppBundle zip.
- **Registration CLI** (`scripts/flo2-rvt.ts`): `flo2-rvt register` (the nickname first, on an app with no data; then the AppBundle, the Activity, their `prod` aliases and the monthly processing cap; never `DELETE /forgeapps/me`) and `flo2-rvt engines`.
- **CI**: lint, typecheck, generated-types check, tests, and the add-in build with its AppBundle as an artifact.
- **Monthly checks**: dependency currency with written holds, and the Autodesk watch (repositories, packages and documentation), which opens one issue when anything moved.
