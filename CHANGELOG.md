# Changelog

## 0.17.0 (unreleased)

A drawing set's plans tag their rooms, and a set holds a room schedule and a cover, each on a sheet of its own. The owner settled what a conceptual set holds beyond version 7's views: every plan's rooms tagged and a room schedule, and then a cover. Change-list schema version 8; add-in 0.16.0; report version 2 still (fields added, none changed); contract v9 (change-list version 8; the hidden context, start results and `report_summary` are v8's).

- **Version 8 and the versions before it.** A version 8 `add_drawing_set` tags every plan's rooms, and one that says nothing makes every kind of version 7 and the two new ones, `room_schedule` and `cover` (`DrawingSets.KindsAsked(views, version)`, `TagsRooms`); `views` may name them or leave them out. A version 7 list's set is exactly what it was, with no room tag, no room schedule and no cover, as the schema's `version` rule says every older list reads. `room_schedule` or `cover` in a list below version 8 is refused (`changes[0].views[1]: room_schedule needs version 8; say "version": 8`, the server's `changes.0.views.1`), by the schema's words, the server and the add-in alike; `views` holds 1 to 6 kinds.
- **The plans' room tags** (`DrawingSets.Rooms.cs`; `EditJob.DrawingSet.cs` `TagRooms`). Each plan the set makes tags every room Revit placed on its level (its `Location` a `LocationPoint`; `ToTag`) at its point: `Document.Create.NewRoomTag(new LinkElementId(room.Id), new UV(p.X, p.Y), plan.Id)`, each in a sub-transaction of its own, so a tag Revit refuses, or makes none of, is counted out and the others go on. The tag type is the model's default for Room Tags (`Document.GetDefaultFamilyTypeId`), which `NewRoomTag` takes, else the first it holds by family then type, set by `ChangeTypeId` (`ChooseRoomTagType`). A model that holds no room tag type still gets its plans, each saying why its rooms are not tagged. Each plan says `rooms_on_level`, `rooms_tagged` and, when fewer, `rooms_why` (`RoomsWhy`: "the model holds no room tag type, so none of the 3 rooms placed on level "Level 1" is tagged"; "Revit would not tag 1 of the 3 rooms ... (room 102: ...)"), which makes the plan not as asked and the set `applied_in_part`.
- **The room schedule** (`room_schedule`): `ViewSchedule.CreateSchedule(doc, new ElementId(BuiltInCategory.OST_Rooms))`, named `Room Schedule` (given (2), (3) ... as any view's name), its fields Level, Number, Name and Area found among `ScheduleDefinition.GetSchedulableFields()` by `ROOM_LEVEL_ID`, `ROOM_NUMBER`, `ROOM_NAME` and `ROOM_AREA` (one Revit does not offer is left out, saying why), sorted by level then number (`AddSortGroupField`), and a grand total row of the count and the area (`ShowGrandTotal`, `ShowGrandTotalTitle`, `ShowGrandTotalCount`, the Area field's `DisplayType` `Totals` where `CanTotal`). On a sheet of its own in a new series, `A-601` (the US National CAD Standard's sheet type 6, schedules), with the set's title block. It says how many rooms it lists (`rooms_scheduled`, Revit's collector over the schedule), and a model with no room still gets it, a note saying the model holds none.
- **The cover** (`cover`; `DrawingSets.Cover.cs`): sheet `A-001`, a new series, A-0xx (type 0, the general sheets; sheet numbers are now written in three digits), named `Cover Sheet`, which `sheets.pdf` prints first. On it a sheet index, `ViewSchedule.CreateSheetList(doc)`, named `Sheet Index`, of every sheet the model holds by Sheet Number and Sheet Name (`SHEET_NUMBER`, `SHEET_NAME`), sorted by number, since `sheets.pdf` prints the model's other printable sheets too; and one text note, `TextNote.Create` of the model's default text note type (`GetDefaultElementTypeId(ElementTypeGroup.TextNoteType)`, or the first it holds), wrapped to six inches within the widths its type allows, under the index or beside it where it does not fit under it, its words one constant (`DrawingSets.CoverNoteWords`): "Conceptual drawing set of *name*: drawings of the model to look the design over, not for permit or construction.", the name the Project Information's; a model that holds none, or only a template's placeholder `Project Name`, gets "Conceptual drawing set: drawings of the model to look the design over, not for permit or construction." (`DrawingSets.CoverNoteWordsUnnamed`), never the model's file name, which in Design Automation is always `input.rvt`. The set makes it last, so its index lists every sheet the set made; its entry comes last in the report's `sheets`. A model that holds no text note type gets its cover without the note, saying why (`note_why`), which makes the cover not as asked.
- **Placing a schedule** (the room schedule and the cover's index; `PlaceSchedule`, one layout for both): at the top-left of the usable area, by `ScheduleSheetInstance.Create`. One taller than the area is split into the fewest segments that each fit its height (`ScheduleSegments`: its body rows, from `ViewSchedule.GetScheduleHeightsOnSheet`, packed in order under a title and column headers each segment repeats), by `ViewSchedule.Split(int)` with every segment but the last set to that height (`SetSegmentHeight`, so rows flow on, as an even split alone would leave the last segment the tallest), each segment placed by its index and set side by side, a quarter inch apart (`SideBySide`), moved by its box read on the sheet (`ScheduleSheetInstance.Point`). One that does not fit across either is placed anyway and says why (`ScheduleFitWhy`, `CoverFitWhy`). It fits as any view does, the box of all it holds (`viewport_min_ft`, `viewport_max_ft`) within the usable area; it has no scale, crop or far clip of the set's.
- **The report**, fields added, all optional, so a report of 0.15.2 or of a version 7 list reads as it did: the set's `tags_rooms`, `room_tag_type`, `room_tag_type_was`; per plan `rooms_on_level`, `rooms_tagged`, `rooms_why`; the room schedule's and the cover's `schedule_fields`, `segments`, `schedule_segments` (`segment`, `instance_id`, `min_ft`, `max_ft`); the schedule's `rooms_scheduled`; the cover's `sheets_listed`, `note_placed`, `note_why`, `note_id`, `note_text`, `note_min_ft`, `note_max_ft`. A rolled-back set clears them.
- **Invariants** (`DrawingSets.Problems`, run by `ReportCheck`): a version 8 plan's `rooms_tagged` is no more than its `rooms_on_level`, with a why when fewer and none when not; a plan of an older list's set says neither; the room schedule and the cover come only of a version 8 set, are placed by one schedule instance per segment, numbered from 0, fit as the other views do (each segment, and the cover's note, within the usable area), name no scale, crop, far clip or viewport, and say how many rooms or sheets they list, or why not; a cover says whether its note was placed, with a why when not; the set names a room tag type only when its plans tag rooms.
- **The words**: the schema (`version`, `DrawingSetView`, `AddDrawingSet`, its `views`), the README, the edit and new-model tools' texts and the change list's words (version 8).
- **Add-in 0.16.0**: an app set up with add-in 0.15.2 (flo2-rvt 0.16.2) reads `outdated` until its next one-time setup, which flo2.io offers. The Activities' inputs and outputs are unchanged.
- **Choices the spec left open**: the cover's entry is last in `drawing_set.sheets` and `views_asked` (it is made last, so its index lists every sheet), though its sheet prints first; its sheet is named `Cover Sheet` and its index `Sheet Index`; a plan's untagged rooms and a cover's missing note are kept in fields of their own (`rooms_why`, `note_why`) and make the set `applied_in_part`; a split schedule is laid out with `SetSegmentHeight` beside `Split(int)`; the note is under the index, beside it when that overruns.
- **Not yet run in cloud Revit**: no live job was started. A live run is needed to confirm that `NewRoomTag` takes the model's default room tag type in Design Automation, that `GetScheduleHeightsOnSheet` and `Split(int)` with `SetSegmentHeight` lay a tall schedule out as computed (whether each segment repeats the title), that `FilteredElementCollector(document, scheduleId)` passes the rooms and sheets a schedule lists, where `TextNote.Create`'s note and a schedule instance's box stand on the sheet, and what the project name reads in a model made in Design Automation (its file there is `input.rvt`, so a model with no Project Name is named `input`).
- **Tests**: the shared cases of version 8 (both sides; the case of a later version now says 9). The add-in's logic (`addin/tests/DrawingSetTests.cs`): which kinds a version asks for; the check's refusals; A-601 and A-001 numbered and named; the plans' rooms tagged and why not; the schedule's fields, segments and fit; the cover's index, note and fit; the invariants of each; and the made-up report flo2 reads (`server/test/fixtures/sample-edit-report-drawing-set.json`), now add-in 0.16.0's of a version 8 list: twelve views, each plan's rooms tagged, the room schedule on A-601 and the cover on A-001. The server: the version 8 rules, the generated types, the schema's words, a version 8 list uploaded as approved and a version 7 one naming `room_schedule` or `cover` refused before Autodesk is asked, the made-up report's plans, schedule and cover, and the tools' texts. On 0.16.2, 17 of 349 server tests fail and the add-in's logic tests cannot compile (`ScheduleSegment` and the rest are not there).

Sections keep `CreateSection`'s box and far clip as 0.15.1 set them.

## 0.16.1 (unreleased)

A drawing set's sections look the way asked, and each elevation and section sees past the building's far side, read back. Two defects the first live drawing set found (2026-11-10, add-in 0.15.0, Autodesk's `rac_basic_sample_project.rvt`; flo2-rvt's design: `fact:root-cause-a-drawing-sets-sections-look-the-wrong-way-because-createsections-basisz-is-the-direction-the-view-looks-2026-11-10` and `fact:root-cause-a-drawing-sets-north-elevation-shows-no-house-because-its-far-clip-stops-short-and-nothing-reads-it-back-2026-11-10`), of one class: a Revit convention assumed and not read back. Add-in 0.15.1; change-list version 7 still; report version 2 still (fields added, none changed); contract v8 unchanged.

- **The sections.** `ViewSection.CreateSection` says "The view direction of the resulting section will be sectionBox.Transform.BasisZ ... The right hand direction will be computed so that (right, up, view direction) form a left handed coordinate system ... The far clip distance will be equal to the difference of the z-coordinates of BoundingBoxXYZ.Min and BoundingBoxXYZ.Max", and `View.ViewDirection` is "The direction towards the viewer" (Revit 2024's `RevitAPI.xml`, 2024.3.60). So `CreateSection`'s view direction is the way a section LOOKS, `View.ViewDirection` its opposite, and the viewer and the cut stand at the box's `Min.Z`, its far clip at `Max.Z`. Add-in 0.15.0 handed it `BasisZ` toward the viewer, its cut at `Max.Z`: A-301 (east-west, asked to look north) came back looking south (`view_direction` (0, 1, 0)), its cut -72.930938 ft off the middle, the box's `Min.Z`; A-302 (north-south, asked to look east) looking west, -67.187753 ft. Revit's view direction and `View.Origin` of both read, to 0.001 ft, as the cut face's lower-left corner at `Min.Z` by that convention. Now `DrawingSets.Section`'s `BasisZ` is the way the section looks (north for the east-west cut, east for the north-south), `BasisY` up, `BasisX` = `BasisY` x `BasisZ` (a right-handed, orthonormal frame; Revit computes the screen's right itself, and the box is the same either side of its middle), `Min.Z` = 0 the cut through the middle and `Max.Z` the far half and the margin; `SectionSpec.Looking` is the compass point `BasisZ` points to. The read-back of the cut is unchanged, and should now read 0.
- **The far clips.** The north elevation (A-201) printed a tree and terrain and no level, grid or house, while the other three printed the house: its far clip stopped short of the building, though setting a crop box moves "the crop region and far clip plane to the smallest values which will completely contain the 3D box", and nothing read it back, so the report said made, placed and fits. Whether its crop was computed in a frame other than Revit's or Revit left its far clip where it was is not established. Now, once cropped, each elevation and section has its far clipping turned on and its far clip set to the depth it needs: from its plane (an elevation's marker, a section's cut) along the way it looks to the building's far side, and the margin (`DrawingSets.ElevationDepth`, `SectionDepth`, `PlannedDepth`; from Revit's own `View.Origin` along the opposite of `View.ViewDirection` where that is further, `DepthNeeded`). On the live building the north elevation needs 18.26 ft (its marker's offset) + 132.60 ft (the building's depth) + 6.63 ft (the margin) = 157.49 ft. The parameters, which `RevitAPI.xml` names only by their labels: `VIEWER_BOUND_ACTIVE_FAR` "Far Clip Active" (set to 1 where it reads 0), `VIEWER_BOUND_FAR_CLIPPING` "Far Clipping", whose values are `BackClippingParam`'s ("The allowed values for the VIEW_BACK_CLIPPING and VIEWER_BOUND_FAR_CLIPPING parameters": `NoClip`, `ClipWithLine`, `ClipNoLine`; one that reads `NoClip` is set to `ClipWithLine`), and `VIEWER_BOUND_OFFSET_FAR` "Far Clip Offset" (the depth, in feet), each where the view holds it and Revit lets it be set, in a part of the change of its own.
- **Read back.** Once everything is set, cropped and placed, each elevation and section's far clipping (on when either parameter says so), its *Far Clip Offset*, the depth it needs, its `View.Origin` and its crop box (`View.CropBox`, taken into the model's axes through its own `Transform`) are read; a far clip short of the depth, or one that could not be read, says so in its `why` ("its far clip reaches X ft, short of the Y ft it needs to hold the building's far side at Z ft and the margin"), as does a crop that leaves the building out across the view, naming the side (`DrawingSets.ReachWhy`, `CropWhy`). A `why` makes the set `applied_in_part`, and flo2's check reads the view as not met, so a short depth no longer passes silently.
- **The report**, per elevation and section (`drawing_set.sheets[]`, fields added): `far_clip_active`, `far_clip_ft`, `depth_needed_ft`, `crop_min_ft` and `crop_max_ft` (its crop box in model terms), and `origin_ft` for an elevation as for a section. All optional: a report of add-in 0.15.0 reads as it did.
- **Invariants** (`DrawingSets.Problems`, run by `ReportCheck`): an elevation or section read as asked whose report says the depth it needs says how far its far clip reaches, and reaches it.
- **The words**: the edit tool's text (which way each section looks; each elevation and section made to see past the building's far side, read back; the report says how far), the README.
- **Add-in 0.15.1**: an app set up with add-in 0.15.0 (flo2-rvt 0.16.0) reads `outdated` until its next one-time setup, which flo2.io offers. Nothing else of the server changed.
- **Not yet run in cloud Revit**: the sections' new box (the convention it rests on was measured live), the far clips set and read back (which of *Far Clip Active* and *Far Clipping* an elevation or section holds, and whether its *Far Clip Offset* is measured from its `View.Origin`'s plane), and why the elevation's crop left its far clip short; the report now gives the crop box in model terms and each view's origin, so the next live run tells.
- **Tests**: the add-in's logic (`addin/tests/DrawingSetTests.cs`): a section's box (`BasisZ` north for an east-west cut and east for a north-south one, the cut at `Min.Z` = 0 and the far side at +depth); as a property over several buildings, by `CreateSection`'s documented convention, Revit's view direction looks the way the set asks, its cut stands 0 ft from the middle, and its far clip is the depth it needs; the live run's own numbers (the convention gives what Revit reported of 0.15.0's box, and the box asked now cuts through the middle); the depth each elevation needs on the live building; the read-back's judgement (`ReachWhy`, `CropWhy`); the new invariants, and a report of 0.15.0 keeping them all; the made-up drawing-set report (`server/test/fixtures/sample-edit-report-drawing-set.json`, which flo2 reads) at add-in 0.15.1, read back through the contract.
